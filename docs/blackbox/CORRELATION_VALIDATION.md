# 1호점 상관 로그 구현·검증 (2026-10-24)

## 결과

수집기와 게임 서버가 같은 Windows PC `172.30.1.43`에서 실행되는 구성을 반영했다.
Omada는 UDP Syslog, 게임 서버는 같은 PC의 JSONL 파일로 수집한다. 별도 telemetry
SQLite와 UTC 타임라인을 추가했으며 두 입력은 설정 예제에서 기본 비활성이다.

실제 컨트롤러 읽기 조회에서 `172.30.1.1`, 버전 `6.2.14.30`, 사이트 `HAS1`,
시간대 `Asia/Seoul`을 확인했다. 컨트롤러 설정은 변경하지 않았으며 자격 증명은
수집기 설정이나 소스에 저장하지 않았다. 논리 사이트 ID는 `store-1`이다.

서버 저장소의 변경은 현재 브랜치 업스트림에 푸시하도록 요구하는 해당 `AGENTS.md`에
따라 `main`의 `07e7eb10cfe79c2fd9dcd8b65ef735c78cd08959`로 커밋·푸시했다.
원격과 로컬 HEAD 일치를 확인했다. 현장 서버 배포/재시작은 수행하지 않았다.
확인한 자동 배포 워크플로의 경로 조건에는 이 서버 변경이 포함되지 않는다.

## 검증 증거

| 검증 | 결과 |
|---|---|
| Python 전체 회귀 | 121개 중 119개 통과, Windows 전용 2개 제외 |
| 실제 Mosquitto 인증/ACL·재연결·중복 저장·ACK | 전체 회귀에 포함, 통과 |
| 실제 UDP, 사이트 거부, DB 동시 초기화, 저장 장애 격리 | 전체 회귀에 포함, 통과 |
| 서버 Express 진단 + 기존 글러브 단절 감시 | 23개 통과 |
| 실제 서버 모듈 HTTP → JSONL → 수집기 → SQLite → 타임라인 | 새 DB에서 3회 통과 |
| 교차 연결 각 회차 | 서버 6건 + UDP 1건 + 장치 1건 저장, 장치 ACK 1건, 수신 오류 0건 |
| PowerShell 구문 | 서비스/서비스 시험 스크립트 통과 |
| 기존 펌웨어·OTA 관련 격리 | 이전 기준 파일 44개 SHA-256 일치 |
| 독립 검토 | 서버 코드, 타임라인, 수집기 통합 교차 검토 완료 |

증거는 작업 트리의 `build/blackbox-validation/`에 보존한다.

- `correlation-final-tests.log`: 최종 Python 실행.
- `correlation-server-tests.log`: 부모 검토자의 최종 서버 실행.
- `correlation-e2e.json`, `correlation-e2e-timeline-1.jsonl` 등: 세 번의 실제 연결 결과.
- `correlation-powershell-parse.log`: PowerShell 파서 결과.
- `correlation-verification.json`: 소스 해시·기준 격리·검증 정보.

검증 중 발견한 초기 DB 동시 생성 경쟁, 최근 시간대 조회 누락, 충돌하는 시간
기준점의 누락, 로그 처리량 상한, 수신기 재시작, 서버 시계 역행 시 재시도 문제는
수정하고 회귀 시험에 포함했다. 개발 Mac에서 1 KiB 정도의 서버 기록 5,000건을
SQLite FULL 모드에 저장한 보조 측정은 약 4,609건/초였다. 이것은 Windows의 처리량이나
게임 지연 보장이 아니며 현장 부하 측정을 대체하지 않는다.

## 현장 적용 순서

1. [수집기 안내](../../tools/windows-blackbox-logger/README.md)의 서비스 설치/갱신
   절차를 사용하고 `config.store1.example.json`을 실제 서비스 설정에 반영한다.
   MQTT 자격 증명은 기존 DPAPI 절차를 사용한다.
2. 게임 서버 변경을 배포하고 실제 실행 테마를 확인한다. 서버 문서
   `docs/BLACKBOX-TELEMETRY.md`에 따라 명시적 설정을 적용한다. 공유 디렉터리 예시는
   `C:\ProgramData\HAS1BlackBox\server-telemetry`이며 서버에는 쓰기, 수집기
   LocalService에는 읽기 권한이 필요하다. 테마는 매장 번호로 추론하지 않는다.
3. 서버 JSONL 수집을 켜고 저장 건수가 증가하는지 확인한다. Omada 수신 준비 후
   HAS1 사이트만 `172.30.1.43:5514/UDP`로 전송하도록 설정한다. Windows 방화벽의
   UDP 5514 인바운드 규칙에서 원격 송신 IP를 확인된 컨트롤러 `172.30.1.1`로 제한한다.
   AP가 직접 보내는 구성이라면 실제 송신 IP를
   확인해야 한다. 기존 원격 로그 목적지가 있다면 먼저 보존한다.
4. Windows와 Omada의 시간 동기화 및 실제 오차를 확인한다. 시험용 장치의
   연결/해제를 재현하고 실제 Syslog 원문·MAC·AP·시각·사이트를 대조한다.
5. [타임라인 안내](../../tools/windows-blackbox-logger/TIMELINE.md)에 따라 장치 DB를
   읽기 전용으로 가져와 장애 시간대를 내보낸다. 보고서의 시계 품질·구간별 잘림과
   이어 읽기 커서를 확인한다.

## 남은 검증과 해석 한계

- 실제 Windows 서비스 설치/권한/방화벽과 현장 Omada 전송·게임 부하는 아직 검증하지
  않았다. PowerShell 구문 검증은 Windows SCM 실행 검증과 다르다.
- 기존 장치 기록에는 UTC 기준점이 없다. 수신 시각에서 uptime을 빼서 사건 시각을
  만들지 않으며, 측정된 기준점이 없으면 미정렬 상태로 보존한다. 이번 작업은 정확한
  장치·서버·Omada 동시성의 완성을 의미하지 않는다.
- 서버와 수집기는 Windows 시계를 공유하지만 Omada와의 오차까지 자동 해결되지는
  않는다. 시간 창의 겹침은 조사 후보이며 원인 확정이 아니다.
- Node 앞단 Apache/PHP는 1초 제한 및 MySQL fallback 경로가 있다. Node의 응답 완료는
  글러브 수신 확인이 아니며, Node 로그가 없다고 장치 정지를 확정할 수 없다.
- UDP 손실은 재전송되지 않는다. 큐·저장 오류 계수를 확인해야 한다. 원문은 제한된
  크기로 보존하며 실제 컨트롤러 표본 없이 RSSI·reason code의 완전 수집을 보장하지 않는다.
- telemetry DB는 자동 삭제하지 않는다. 기본 1 GiB 여유 제한은 추가 진단 쓰기를
  멈추는 보호 장치이며 다른 프로세스의 디스크 사용을 예약하거나 제한하지 않는다.
  원본 파일의 순환 보관과 SQLite 용량 관리가 필요하다.
- 기존 공용 통신 라이브러리·게임 HTTP·OTA 구조는 이번 작업에서 변경하지 않았다.
