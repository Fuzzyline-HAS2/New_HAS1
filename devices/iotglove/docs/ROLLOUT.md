# 조립 전 검증과 8대 설치

2026-09-17 기준. **G1P1~G1P8 총 8대, 16개 보드의 초기 설치를 완료**했다. G1P1은 최초 USB 설치 후 v1→v2 순차 OTA, G1P2~G1P8은 v2 Release의 USB 설치로 완료했다. 이후 MAC 등록은 사용자가 직접 담당하기로 했다. **G1P1~G1P7 총 7대의 두 보드 v2→v3 OTA·새 부팅·Telnet 검증을 완료**했다. G1P8은 USB v2 설치만 확인했다. 세부 실측과 재시도 이력은 [검증 기록](VALIDATION.md)을 따른다.

## 1. G1P1 v1→v2 OTA·Telnet 최초 실증 — 완료

- [x] 등록된 G1P1의 유효한 서버 응답과 비활성 `ready` 상태, 현재 버전·파티션·부팅 증거를 확인했다. 두 대상 Actions 성공과 Release 산출물의 HMAC을 확인했다.
- [x] `github@2:2`로 **Beetle v2 업데이트 → 새 부팅·목표 버전 확인 → TTGO v2 업데이트·새 부팅**을 실증했다. flashing 또는 동일 버전 skip만으로 실제 설치를 판정하지 않았다.
- [x] TTGO 재접속 후 양쪽 펌웨어 2 / 파티션 1, UART 응답, 서버 `valid=1`·`fresh=1`·`esp_version=2`를 확인했다.
- [x] Telnet 첫 접속과 재접속에서 상태·수동 PING 각 2회를 확인했다. 마지막 부팅 후 PING 누계는 45/45회, timeout 0회다. 명시적 Beetle BOOT 원인 값 3, 반복 PING 중 BOOT 이벤트 중복 억제와 로그 출력 중 UART 응답을 확인했다.

최초 업데이트 당시 TTGO v1은 Beetle LOG를 소비하지 않는다. OTA 순서·재부팅 증거는 UART 기록, BOOT 로그·상태·PING은 v2 설치 후 Telnet 기록으로 구분한다. 이번 완료는 전체 OTA 과정을 Telnet에서 관찰하거나 롤백·장애 복구를 실측했다는 의미가 아니다.

## 2. G1P1~G1P8, 총 8대 초기 설치 — 완료

각 장치는 TTGO와 Beetle 한 쌍이다. G1P1은 v1 최초 USB 설치 후 위 OTA로 v2를 확인했다. G1P2~G1P8의 14개 보드는 사용자 지시에 따라 **기존 펌웨어 백업 없이 확정한 v2 Release 이미지로 설치**했다. 실물 라벨·보드 종류·MAC을 대조했고, 서로 다른 USB 포트는 병렬 업로드했다. MAC/IP·업로드 원본 로그는 로컬 장치 목록에 보관하고 공개 문서와 PR에는 해당 주소 목록이나 비밀값을 넣지 않는다.

| 장치 | 초기 설치 확인 |
| --- | --- |
| G1P1 | 두 보드 초기 USB 설치·서버 등록, v2 순차 OTA·Telnet·UART 확인 완료 |
| G1P2~G1P8 | 각 두 보드 v2 USB 설치 완료, 보드당 4영역(장치당 8영역) 해시 검증 통과 |

MAC 등록은 사용자가 직접 담당한다. 아래 실행 상태 대조는 G1P1~G1P7이 대상이며, G1P8의 설치 완료를 OTA·Telnet 실측 완료로 취급하지 않는다.

G1P2~G1P8의 USB 설치에서 다음을 확인했다.

- [x] 실물 라벨·보드 종류·실제 MAC으로 업로드 대상을 식별했다.
- [x] 각 보드의 GitHub Actions Release에서 내려받아 서명을 검증한 `update.bin`과 **동일한 애플리케이션 바이트**, `min_spiffs` 파티션을 사용했다. compile-only 이미지는 설치하지 않았다.
- [x] USB 460800·`--no-fast-flash`로 설치하고 부트로더·파티션·boot_app0·애플리케이션 **네 영역 해시 검증**을 보드마다 확인했다. 설치 대상은 펌웨어 2 / 파티션 1이다.

장치마다 OTA·Telnet 실측을 끼워 넣지 않고 전체 업로드를 먼저 마쳤다. 각 장치 GPIO 리셋 시험은 이번 OTA·Telnet 확인의 선행 조건으로 두지 않는다.

## 3. G1P1~G1P7, 7대 v3 OTA·Telnet 실측 — 완료

- [x] 5대 모두 OTA 전 양쪽 펌웨어 2 / 파티션 1, 올바른 MAC·서버 장치명, 서버 valid/fresh, 신선한 heartbeat와 일치 PING을 확인했다. PING RTT는 13~15ms, timeout은 0이었다.
- [x] 두 대상 v3 Actions 성공과 산출물 서명을 확인했다. v2에서 펌웨어 정수 버전만 변경했고 의존성·파티션 1은 유지했다.
- [x] 첫 병렬 시도에서 G1P4·G1P7은 Beetle→TTGO 업데이트 후 양쪽 펌웨어 3 / 파티션 1과 새 부팅 ID, Telnet 재접속·PING을 확인했다.
- [x] 첫 시도에서 Wi-Fi 연결에 실패한 G1P3·G1P5·G1P6도 재시도 후 양쪽 v3와 새 부팅, Telnet 통과를 확인했다. G1P3은 첫 재시도에서 연결 성공 뒤 상세 단계가 확인되지 않은 OTA 실패가 한 번 더 있었다. 재시도 전 G1P6의 UART 거부 라인 누계 1건도 기록했다. [OTA 실패 조사 항목](https://app.notion.com/p/3dd0bd3810bf8191a874c60963215fcc)에서 원인과 재현 조건을 계속 추적한다.
- [x] 5대 각각 양쪽 펌웨어 3 / 파티션 1, 기준과 다른 두 보드 boot ID, 서버 valid/fresh, Telnet 일치 PING을 확인했다. 최종 관찰의 PING RTT는 14~15ms이며 timeout·UART 거부 라인·송신 실패·로그 유실은 각 새 부팅 기준 0이었다. 과거 실패나 거부 누계가 없었다는 뜻은 아니다.
- [x] 이후 추가한 G1P1·G1P2도 각 `u` 1회로 Beetle→TTGO 업데이트를 진행하고 양쪽 펌웨어 3 / 파티션 1, 두 보드의 새 boot ID, 서버 valid/fresh와 Telnet 일치 PING을 확인했다. 두 장치 모두 최종 수동 PING RTT 14ms, timeout·UART 거부 라인·송신 실패·로그 유실 0이었다.

사용자가 성공 확인 후 G1P4·G1P7의 전원을 껐다고 확인했다. 그 뒤 접속 timeout은 전원 OFF 상황으로 구분하며 이미 확보한 양쪽 v3·새 부팅·Telnet 통과 기록을 무효로 하지 않는다. **7대의 완료는 각 장치가 연결돼 있을 때 확보한 OTA·재접속 기록의 대조 결과**이며, 7대를 동시에 온라인으로 확인한 시험은 아니다. G1P8의 OTA·Telnet은 이번 실측에 포함하지 않는다.

게임 전체·BLE 매핑·배터리 보정은 아래 후속 검증에서 관리하며, 이번 초기 설치·등록의 추가 선행 조건으로 두지 않는다.

## 4. 이후 개발: PR·Actions·운영 OTA

v2 초기 설치와 G1P1~G1P7의 v3 OTA·Telnet 실측은 완료됐다. 이후 변경은 다음 절차로 진행한다.

- [ ] PR에서 소스·문서·서명/보관 정책을 독립 검토하고 host/Python 테스트 및 TTGO 본게임·훈련·Beetle 컴파일 결과를 확인한다. [서버 계약](SERVER_CONTRACT.md)의 미해결 항목과 실측 범위를 명시한다.
- [ ] 변경 반영 후 기존 `Deploy Firmware` 규칙으로 두 대상을 하나씩 배포한다. 정수 버전은 CI가 증가시키며 고정/보관 릴리즈의 자산·서명·출처를 확인한다. 여러 실행을 동시에 대기열에 넣지 않는다.
- [ ] 새로운 운영 OTA는 먼저 한 쌍의 목표 버전·새 부팅·재연결을 확인한 뒤 설치된 나머지 7대로 확대한다. 두 보드 업데이트는 원자적이지 않으므로 부분 성공 시 각 실행 버전을 확인하고 복구한다.
- [ ] 설치 버전과 검증 일자를 로컬 목록에 갱신하고 공개 기록에는 주소·비밀값을 제거한 결과를 남긴다. 게시·설치·실측 완료를 구분한다.

## 5. 별도 후속 검증 — 미완료

- 실제 역방향 롤백·한 보드만 변경·동일 버전 skip, 없는 버전·서명 오류·파티션 불일치·통신 단절·NVS/플래시 기록 중 전원 손실의 처리.
- 전체 게임/훈련 사이클, 칩·버튼·LED·진동과 서버 계약의 미해결 구간.
- 실제 비콘 매핑, 방 이동·경계·비콘 소실과 위치/진동 처리.
- 배터리 ADC 배선·분압비·멀티미터 보정 및 부하별 확인. 현재 측정 기본 비활성 상태를 측정 완료로 기록하지 않는다.
- WDT 원인 판독을 포함한 리셋 장애 시나리오. v2 BOOT 원인 값 수신만으로 과거 리셋 시험의 원인을 확정하지 않는다.

후속 검증에서 확인되는 문제·기획 차이는 재현 조건과 함께 별도 서브아이템으로 나누어 개발한다.
