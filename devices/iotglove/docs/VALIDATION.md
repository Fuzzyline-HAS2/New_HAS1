2026-09-16, `codex/iotglove-firmware`, New_HAS1 기반 `6072e43`. 기존 HAS1_duct 미커밋/미추적 파일 12개의 SHA-256이 작업 전후 동일하다. 아래 1차 검증은 로컬 소프트웨어 검증이며 당시 장치나 운영 서버에서 측정한 결과는 아니다. 이후 USB·OTA·Telnet 실측은 날짜와 단계별로 별도 기록한다.

- ESP32 Arduino **3.3.11**로 TTGO 본게임·훈련, Beetle 컴파일 통과.
- 별도 임시 키/소스 복사본에서 compile-only 매크로를 제거하여 **실제 OTA 경로를 포함한 링크/용량 검증** 통과. 완성 시 소스/공용 라이브러리 해시와 빌드 복사본 일치 확인.

## 게임·위치·배터리 현장 검증 전 설정

아래 설정과 통합 게임 검증은 후속 항목이다. 총 8대 초기 설치와 G1P1~G1P7의 OTA·Telnet 실측 완료 범위는 [설치 계획](ROLLOUT.md)에서 별도로 관리한다.

1. TTGO 실물 배터리 종류/셀 수, ADC 배선, 실제 분압비와 보정 범위를 `hardware_config.h`에 반영한다. 기본값은 측정 보고 비활성이다.
2. 실제 제단·생명장치의 `HAS3:장치명`을 Beetle `beacon_map.h`의 방 매핑에 넣는다. 현재 방 이름/별칭 기본값이 현장 ID와 같다고 가정하지 않는다.
3. GPIO12 부팅 LOW 유지, Beetle GPIO1 pull-down, 공통 GND, UART 교차 연결, 모터 드라이버를 대조한다. 회로도 심벌의 물리 핀 4가 GPIO1이며, 기존 GPIO3 가정은 아래 실기 기록에서 정정했다.
4. 서버 MAC 등록과 G1/G2 장치명, `tagger_name`, 역할/시간/봉헌/개방 필드를 확인한다. 두 보드 첫 USB 설치는 빌드와 같은 min_spiffs 파티션을 사용한다.

## 2026-09-17 버전 지정 OTA·롤백 추가 검증

기존 수동 배포·정수 버전·고정 태그를 유지하고 두 글러브 대상에만 비덮어쓰기 버전 보관 릴리즈를 추가했다. `github@12:7`은 TTGO 12·Beetle 7, `github@12`는 두 보드 모두 12를 뜻한다. 명령과 실제 산출물 형식은 [BUILD.md](BUILD.md)를 따른다.

- 실제 펌웨어의 C++ 호스트 테스트 실행 파일 **9개 통과**. 추가 항목은 엄격한 버전/메타데이터 파서, 실행 중 목표 고정·다음 명령 보관, Beetle NVS 목표 버전/파티션/새 부팅 복구다. 기존 peer 테스트에는 이전 버전 롤백·동일 버전 skip·틀린 목표·완료 후 버전 변경/연결 만료를 포함했다.
- Python 테스트 **14개 통과**. 메타데이터 HMAC, 잘못된 이미지/파티션 서명, 버전/보드 범위, 기존 보관 파일 충돌 시 쓰기 없음, 같은 내용 재시도, 중단된 draft 재개, 소스와 커밋 일치, 다른 호스트로 토큰 전달 방지를 확인했다. GitHub 쓰기는 모의 API로 검증했으며 실제 게시하지 않았다.
- 독립 검토에서 단계 사이 게임/탐색 전환 또는 서버 단절 시 OTA 대기가 게임 처리를 계속 막는 문제를 수정했다. Beetle 완료 후 부적합 페이즈에서는 남은 TTGO 단계를 취소하고, 서버 대기는 작업 시작부터 5분으로 제한했다. 시작 전 TTGO Wi-Fi 단절은 큐를 비운 뒤 실패 처리한다. 이미 쓰기 중인 플래시는 중간에 취소하지 않는다.
- 작성 담당과 다른 검토자가 최종 TTGO/Beetle 상태 처리, 서명 메타데이터와 이미지 검증, 보관 릴리즈 정책 및 문서를 재검토했다. 최종 검토 범위의 미해결 발견 사항은 없다.
- ESP32 core **3.3.11**, 위와 같은 격리 의존성으로 최종 소스 컴파일 통과. 두 본게임 보드는 compile-only 매크로 없이 실제 신규 OTA 다운로드/서명/쓰기 경로까지 링크했다. 임시 합성 키만 사용했고 실제 키나 원본 버전을 변경하지 않았다.

최종 TTGO/Beetle 빌드 소스 해시를 작업 파일과 대조했다. 기존 HAS1_duct 파일 12개의 해시도 작업 전과 동일하다. Actions YAML/Bash와 변경 파일 공백 검사를 통과했다. 원본 두 스케치의 `FIRMWARE_VER=1`, `PARTITION_VER=1`은 유지했다.

실기기에서는 두 버전을 실제로 보관한 뒤 순방향 업데이트·역방향 롤백·한 보드만 변경·동일 버전 skip·없는 릴리즈·서명 오류·파트 버전 불일치·Wi-Fi/UART 단절·NVS/플래시 기록 중 전원 차단을 확인해야 한다. 두 보드 업데이트는 원자적이지 않으므로 TTGO 단계 실패 시 Beetle만 변경될 수 있다. 완료 확인에는 목표 버전 및 재부팅 증거가 필요하며, 전원 차단/실제 무선 환경의 복구는 아직 실측하지 않았다. 이 OTA 소프트웨어 검증 단계에서는 커밋/푸시·원격 Actions·Release 게시·장치 USB/OTA를 수행하지 않았다. 이후 USB 설치 결과는 다음 절에 기록한다.

## 2026-09-17 최초 USB 설치와 TTGO 복구

- G1P1 테스트 글러브의 TTGO와 Beetle에 실제 배포 키로 빌드한 펌웨어 1 / 파티션 1을 설치했다. 당시 Beetle 리셋 입력은 GPIO3으로 빌드했다. 키는 기존 Release의 이미지·서명과 대조했으며 저장소나 로그에 값을 기록하지 않았다.
- 두 보드 모두 460800 업로드와 네 영역 해시 검증을 통과했다. 변경 영역은 먼저 백업했고, NVS를 포함한 전체 플래시 지우기는 하지 않았다.
- TTGO는 Origin 모드 부팅 및 Wi-Fi 연결, Beetle은 `firmware=1` 부팅을 확인했다. 각각 20초 관찰에서 반복 애플리케이션 부팅·panic·brownout은 관찰되지 않았다.
- 사용자가 이후 TTGO에 다른 펌웨어가 올라갔다고 확인하여 검증된 글러브 이미지를 다시 기록했다. 이 복구에서는 이전 업로드 캐시를 사용하지 않도록 `upload.extra_flags=--no-fast-flash`를 지정했고, 네 영역 해시·Origin 부팅·Wi-Fi 연결을 새로 확인했다.
- 완제품 구조에서 Beetle USB 접근이 어려워, 회로도 정정 전 진단은 TTGO USB를 통한 UART 응답과 부팅 ID로 수행했다. GPIO1 정정 후에는 사용자가 Beetle USB 연결·업로드를 명시적으로 지시하여 직접 설치가 허용됐다. 이전 USB 연결 단절이나 다른 TTGO 펌웨어로 실행한 검증을 글러브 펌웨어의 결함 또는 연동 성공 증거로 취급하지 않는다.

이 USB 설치 기록은 BLE 위치, 게임 사이클, 배터리 보정, 실제 두 보드 OTA·롤백 검증을 대신하지 않는다. 해당 현장 검증은 계속 남아 있다.

## 2026-09-17 TTGO USB를 통한 Beetle 진단

- `s`/`?` 상태 조회, `p` 요청 ID가 일치하는 PING/HELLO 응답 확인, `b` 실제 펄스 이후 새 부팅 관찰을 추가했다. Beetle v1과 IG1 프로토콜은 변경하지 않았다.
- 호스트 테스트 실행 파일 **10개 통과**. 오래된 응답·다른 요청 ID·HEART 단독·펄스 이전 PING·알 수 없는 기준 부팅·시간 초과·타이머 wraparound·고정 출력 큐를 검증했다. 별도 검토자가 실제 펄스의 기준 부팅 캡처, 게임/OTA 영향, 출력 상한과 현재 요청/이전 펄스 결과 구분을 검토했다.
- 최종 production Origin 빌드는 프로그램 **1,097,685 / 1,966,080 bytes**, RAM **54,208 / 327,680 bytes**다. 훈련 compile-only 빌드는 프로그램 **386,681 bytes**, RAM **33,068 bytes**로 컴파일을 통과했다. 훈련 검증 바이너리는 설치하지 않았다.
- 실제 배포 키를 포함한 TTGO 최종 바이너리 1,097,840바이트와 소스 21개 해시를 대조하고 460800으로 업로드했다. 네 영역 해시 검증, Origin v1 부팅·Wi-Fi 연결, 진단 명령 출력을 확인했다.
- 배터리 연결 전 TTGO USB만 사용한 첫 실기 결과는 **Beetle UART 미연결**이었다. 12초 상태/프로브 관찰에서 `known=0`, `online=0`, `rx_bytes=0`이며 PING은 timeout이었다. TTGO 송신 카운터 증가는 실제 배선에서 전기 신호를 측정한 결과가 아니다.
- 같은 전원 조건의 추가 24초 관찰에서 `b`의 HIGH 150ms 출력 처리 로그를 확인했으나, 15초 기한 내 응답이 없어 `timeout_not_confirmed`였다. 끝까지 RX는 0바이트였다. 기준 부팅과 새 HELLO가 없으므로 당시 결과만으로 Beetle 재부팅 성공이나 WDT 원인을 확인했다고 판정하지 않는다.

| G1P5 | 재시도 후 완료 | 199 / 199 | 14ms |
| G1P6 | 재시도 후 완료 | 105 / 105 | 15ms |
| G1P7 | 첫 시도 완료 | 76 / 76 | 15ms |

이 표의 각 최종 부팅에서 timeout·UART 거부 라인·송신 실패, USB/Telnet 유실 바이트·거부 명령·진단 로그 유실은 모두 0이었다. 위에 기록한 업데이트 전 실패와 G1P6의 이전 부팅 거부 누계 1건은 그대로 보존한다. G1P4·G1P7은 성공 확인 후 사용자가 전원을 껐으므로, 후속 접속 timeout을 펌웨어 결함으로 분류하지 않는다. 두 장치의 전원 OFF 전 통과 기록과 나머지 3대의 최종 통과 기록을 장치별로 대조했으며, 5대를 같은 순간에 모두 재접속한 시험은 아니다.

## 2026-09-17 G1P1·G1P2 추가 검증 및 7대 v3 OTA·Telnet 완료

사용자가 G1P1·G1P2를 추가 연결해 시험 목표를 **G1P1~G1P7 총 7대**로 확대했다. 두 장치 모두 OTA 전 양쪽 v2 / 파티션 1, 서버 장치명·valid/fresh, 신선한 heartbeat와 수동 PING을 확인했다. G1P1의 PING은 191/191회·RTT 14ms, G1P2는 247/247회·RTT 13ms였고 timeout·UART 거부 라인·송신 실패·로그 유실은 0이었다.

G1P1·G1P2에 `u`를 각각 **1회** 전송했다. 두 장치 모두 Beetle 업데이트·새 부팅 확인 뒤 TTGO의 이미지 검증·재부팅 순서를 관찰했고, 이후 별도 Telnet 접속에서 양쪽 펌웨어 3 / 파티션 1과 OTA 전 기준과 다른 두 보드의 boot ID를 확인했다. 최종 서버 장치명·`valid=1`·`fresh=1`, 신선한 heartbeat와 새 수동 PING의 일치 HELLO도 확인했다.

| 장치 | 최종 부팅 후 누적 PING 일치 / 전송 | 수동 PING RTT | timeout |
| --- | --- | --- | --- |
| G1P1 | 98 / 98 | 14ms | 0 |
| G1P2 | 84 / 84 | 14ms | 0 |

두 장치의 최종 부팅에서 UART 거부 라인·송신 실패, USB/Telnet 유실 바이트·거부 명령·진단 로그 유실은 모두 0이었다. 이로써 **G1P1~G1P7 총 7대, 14개 보드의 v2→v3 OTA·새 부팅·Telnet 검증을 완료**했다. 장치별로 확보한 성공 시점의 기록을 대조한 결과이며, 7대 동시 온라인 시험을 뜻하지 않는다. **G1P8은 두 보드 USB v2 설치만 완료**했고 이번 OTA·Telnet 결과에 포함하지 않는다.

초기 Wi-Fi 연결 실패와 G1P3의 후속 OTA 실패는 재시도 성공과 별개로 [OTA 실패 조사 항목](https://app.notion.com/p/3dd0bd3810bf8191a874c60963215fcc)에서 원인을 계속 추적한다. 게임 전체·BLE 위치·배터리 보정과 추가 리셋·롤백·전원 손실 시나리오는 후속 검증으로 남긴다. 원본 로그와 개별 MAC/IP는 로컬에 보관하며 공개 문서에는 포함하지 않는다.
