# 발전기 배선 개수 절대값 동기화

완료 전송은 [조건부 완료 복구](COMPLETION_RECOVERY.md)를 따릅니다. 저장된 완료 요청이 미해결이면 배선 CAS 쓰기를 보류해 원래 revision을 먼저 판정합니다.

발전기에서 확정한 **실제 연결 개수 0~4를 서버 `battery_pack`에 그대로 저장**합니다. `+1`/`-1` 누적 전송은 사용하지 않습니다. LG의 완료 기준이 3이어도 실제 4개가 연결되면 4를 저장하고, 4→3→2를 각각 구분합니다. `max_battery_pack`은 완료 여부를 판단하는 기준이며 전송값의 상한이 아닙니다.

## 입력과 완료 판단

- 정적으로 할당한 FreeRTOS 입력 태스크가 GPIO 네 개를 4비트 마스크로 읽고 100ms 대기한 뒤 다시 읽습니다. 최근 실제 관측 10개를 저장하며, 누락된 샘플을 뒤늦게 생성하지 않습니다.
- **배선별로 연결 관측이 8/10 이상이면 연결, 해제 관측이 8/10 이상이면 해제**로 판정합니다. 어느 쪽도 8회에 못 미치면 해당 배선은 미확정입니다. 네 배선 모두 확정된 경우에만 연결 개수를 합쳐 서버에 보냅니다. 미확정 구간에서는 화면용 마지막 확정 개수를 유지하지만 새 전송·스타터 진행·완료는 보류합니다. 합계가 같은 샘플이라도 서로 다른 배선이 번갈아 연결돼 있으면 확정되지 않을 수 있습니다.
- 초기화 후에는 실제 샘플 10개 이상과 첫 관측부터 1초 경과를 모두 요구합니다. 정상 100ms 주기에서는 0ms부터 1000ms까지 관측한 뒤 최근 10개를 판정합니다. 이후에는 매 샘플마다 슬라이딩 창을 다시 판정하므로 지속된 변경은 일반적으로 새 샘플 8개(약 800ms)에 반영됩니다. 1초 무잡음 상태를 새로 요구하지 않습니다.
- 250ms 공백 초기화와 마지막 샘플의 시간 만료는 없습니다. 긴 공백만으로 관측 개수를 늘리거나 확정하지 않습니다. 초기화 후 1~2개 샘플만으로는 공백이 길어도 확정되지 않습니다. 반면 이미 확정된 창은 태스크가 멈춰도 시간만으로 만료되지 않으므로, 관측하지 못한 구간의 실제 상태는 보장하지 못합니다. 입력 태스크 생성 실패 시에는 전송·완료를 허용하지 않습니다.
- 입력 태스크는 GPIO와 상태기계만 처리하고 HTTP, JSON, 로그, 음원 처리는 하지 않습니다. 메인 루프는 `portMUX` 임계 구역에서 복사한 스냅샷을 사용하므로 HTTP/음원 대기 중에도 스케줄링이 가능한 태스크는 관측을 이어갑니다.
- `WireResetTracking()`은 설정/대기/새 충전 사이클/기기 이름 변경에서 전체 투표 창과 확인 상태를 초기화합니다. 이전 창을 새 라운드에 가져오거나 원시 개수를 즉시 전송하지 않습니다.
- 물리 필터 확정값과 서버 확인값은 분리합니다. 전송 실패 시 최신 필터 확정값을 재시도합니다. 이전 증감 이벤트를 순서대로 재생하지 않습니다. 미확정 창에서는 서버 ACK가 있어도 진행하지 않습니다.
- 연결·해제·완료에 **동일한 8/10 필터 결과**를 사용합니다. 완료 함수 진입 전, 안내 음원 뒤, 배터리 완료 요청 뒤에 필터 상태와 서버 ACK를 다시 확인합니다. 완료 검사에서 GPIO를 추가로 읽거나 단일 원시값으로 투표 결과를 뒤집지 않습니다. 따라서 마지막 원시 샘플이 달라도 8/10 결과가 유효하면 완료를 허용할 수 있습니다. 같은 사이클에서 이미 시작한 안내 음원과 발행한 요청은 재확인 때문에 반복하지 않습니다.
- 서버 폴링의 `battery_pack`만으로 완료하지 않습니다. 기준 미달·미확정 창·서버 확인 미완료이면 스타터 진행과 새로운 `BatteryFinish()`/`StartFinish()`를 보류합니다. 이미 발행된 수리 완료는 취소하지 않습니다.

## 서버 계약

기존 `Send&column=battery_pack`는 다른 장치가 사용하므로 의미를 바꾸지 않습니다. 발전기는 같은 `/has2.php`에 전용 요청을 사용합니다.

```
GET ?request=GetGeneratorWires&mac=<MAC>&key=<device_name>
GET ?request=SetGeneratorWires&mac=<MAC>&key=<device_name>&value=<0..4>&epoch=<UUID>&revision=<expected>
```

문자열 쿼리 값은 URL 인코딩합니다. 성공 응답은 HTTP 200이고 다음 필드를 최상위 객체에 담습니다.

```json
{
  "success": true,
  "device_name": "LG",
  "battery_pack": 3,
  "epoch": "11111111-1111-1111-1111-111111111111",
  "revision": 8,
  "game_state": "activate",
  "device_state": "activate",
  "max_battery_pack": 3
}
```

- `epoch`은 길이 36인 UUID, `revision`은 0~4294967295의 JSON 정수입니다. 기기 이름·문자열 타입·숫자 타입을 검사하며 숫자 문자열/불리언/소수는 확인값으로 받지 않습니다.
- GET/409의 `battery_pack`은 과거 누적 오류를 교정할 수 있도록 signed int32 범위를 읽습니다. 실제 SET 성공 확인은 요청한 0~4와 완전히 일치해야 합니다. 완료 기준은 1~4만 유효합니다.
- SET은 현재 epoch/revision과 일치할 때만 반영됩니다. 성공 응답은 요청 epoch와 같고 revision이 요청값보다 커야 합니다. 동일 개수의 SET도 revision을 소비합니다.
- 충돌은 HTTP 409, `success:false`, `error:"CONFLICT"`와 동일 형태의 현재 스냅샷을 반환합니다. 400/403/404/5xx, 시간 초과, 잘못된 응답도 모두 미확인 상태로 남습니다. 증감 방식으로 돌아가는 fallback은 없습니다.
- 서버 revision이 상한에 도달하면 실패 처리하며 임의로 0으로 돌려 오래된 요청을 허용하지 않습니다.

처음 시작하거나 충전 사이클/기기 이름이 바뀌면 GET 후 동일 값이어도 CAS SET을 한 번 수행합니다. ESP 재부팅 전에 보낸 요청이 아직 서버에 지연되어 있을 수 있기 때문입니다. SET 타임아웃 뒤 GET 값이 이미 맞더라도 같은 CAS 확인이 필요합니다. 이때 새 revision을 확보하여 이전 지연 요청을 거절하게 합니다. 확인된 값이 유지되는 동안은 GET/SET을 반복하지 않습니다.

정상 경로에는 일률적인 2초 전송 간격을 두지 않습니다. 새로 확정된 개수는 메인 루프가 동기화 처리를 실행할 수 있는 시점에 전송하며, 한 시도 안에서 GET 후 SET을 연속 수행할 수 있습니다. 실패·충돌·응답/상태 불일치로 확인하지 못한 경우에만 마지막 시도 종료 후 최소 2초를 두고 재시도합니다. 재시도는 GET으로 문맥을 확인한 뒤 최신 확정값만 SET합니다. 일반 상태 변경은 CAS 문맥을 새로 조회하되 완료 음원이나 스타터 진행을 새 사이클로 초기화하지 않습니다.

전용 응답은 전체 장치 데이터가 아니므로 `my` 전체에 덮어쓰지 않습니다. 서버 epoch/상태가 달라지면 기존 `ReceiveMine()`과 `DataChanged()`로 전체 상태를 다시 적용합니다. 그 갱신이 실패하더라도 ACK를 확보하지 못한 채 완료를 진행하지 않습니다. 새 epoch를 받았다는 이유만으로 `repaired`/`repaired_all`을 다시 충전 단계로 돌리지 않습니다.

## 배터리 완료 안내 음원

`BatteryFinish()`는 음원이 끝날 때까지 한 호출 안에서 기다리지 않습니다. `Preparing`에서는 이전 DFPlayer 이벤트를 호출당 최대 8개 비우고, 준비가 끝나면 안내 음원을 한 번 재생해 `Playing`으로 넘어갑니다. 준비 중 이벤트가 계속 쌓이면 2초 제한 후 음원을 생략하고 다음 완료 검사를 진행합니다. `Playing`도 호출당 최대 8개 이벤트를 확인하며, 재생 완료 이벤트 또는 재생 명령 후 2초 경과 중 먼저 확인한 조건으로 대기를 끝냅니다.

DFPlayer 완료 이벤트에는 명령 ID가 없으므로 새 음원 재생을 시작한 뒤 늦게 도착하는 이전 곡의 완료 이벤트까지 완전히 구분할 수는 없습니다.

대기는 메인 루프의 여러 호출에 걸쳐 진행됩니다. DFPlayer 명령 전송과 드라이버의 UART 처리 자체는 짧게 블로킹할 수 있으며, 다른 기존 음원 대기 함수 전체를 비동기로 바꾼 것은 아닙니다. 음원 대기 종료 후에도 배선 안정값과 서버 ACK를 다시 확인해야 스타터로 넘어갑니다.

## 통신과 로그

`wire_http.ino`는 발전기 단일 network worker에 요청을 넣고 메인에서 결과를 검증합니다. worker는 공용 HTTPClient 인스턴스를 재사용하지 않고 자기 소켓을 소유합니다. `my` 적용은 메인이 담당합니다. 서버 주소는 `GENERATOR_SERVER_URL`을 사용하며 공용 HAS2_Wifi 소스와 배포 의존성은 변경하지 않습니다.

worker의 connect/write/header/body에는 합산 2000ms 예산을 사용합니다. 소켓 정리는 이 예산을 넘길 수 있으므로 전체 호출 시간의 절대 상한을 보장하지 않습니다. 본문에는 추가 1000ms 제한과 최대 1024바이트 제한을 적용합니다. 응답은 양의 Content-Length가 있는 본문만 허용하고 chunked/길이 없는 응답은 확인 실패로 처리합니다. 상세 transport 제한은 NETWORK_ISOLATION.md와 공용 transport 테스트 문서를 참조합니다.

텔넷에 `[Wire] stable=...`, `[WireSync] confirmed=... revision=...`, HTTP 실패/재동기화 상태를 출력합니다. 모든 샘플을 로그로 쓰지는 않습니다. 별도의 PC 로그 수집기와 기존 텔넷 전송 경로는 변경하지 않습니다.

## 적용 순서와 한계

1. 서버에 GET/SET/CAS 계약이 있어야 합니다. CompleteGenerator와 completion_protocol: 1은 선택이며 없으면 완료는 예전 Send로 갑니다.
2. 실제 서버의 endpoint 응답과 장치 MAC/이름 매핑을 확인합니다.
3. 그 다음 발전기 펌웨어를 빌드/배포합니다. 버전 증가는 기존 배포 워크플로를 사용합니다.
4. 현장에서 LG 3개 완료, 4→3→2, 빠른 연결/해제, 통신 복구, 설정/새 라운드, 수리 완료 후 배선 감시를 확인합니다.

배선 API가 없는 서버에서는 수량 ACK를 얻지 못합니다. 배선 API만 있는 구형 서버는 수량 ACK를 보낼 수 있고, completion_protocol 지원 표시가 없으므로 완료는 v37과 같은 예전 Send 1회로 보냅니다([완료 경로 선택](COMPLETION_RECOVERY.md)). 이번 변경은 배포를 자동 실행하지 않습니다.

이 펌웨어 PR은 PC 로그 수집기와 펌웨어 버전을 변경하지 않으며 서버 PR #87 선배포가 필요하지 않습니다. 현장 실기 검증은 아직 수행하지 않았습니다. 전기적 GND/전원 문제나 Wi-Fi 장애를 해결하지는 않습니다. HTTP 대기는 worker에서 처리하지만 일부 음원/UART 처리는 여전히 메인을 지연시킬 수 있습니다. 입력 태스크의 관측 공백만으로 투표 창이 초기화되지는 않으며, 관측하지 못한 잡음·분리·재연결은 창에 반영되지 않습니다. 같은 배선에서 최근 10회 중 3~7회 연결이 관측되는 모호한 상태가 계속되면 완료가 계속 보류될 수 있습니다. 단일 원시값 재검사를 제거했으므로 실제 분리 직후에도 최근 창에 연결 표가 8개 이상 남아 있으면 완료를 허용할 수 있으며, 이 지연은 연결·해제·완료에 동일 필터를 적용한 의도된 동작입니다. 입력 관측을 분리했더라도 네트워크 응답과 메인 루프 실행 시점에 따라 후속 전환이 늦어질 수 있으므로 연결 후 완료까지 고정된 시간을 보장하지 않습니다. 수량 CAS와 완료는 별도 요청이지만 새 완료 API가 원래 epoch/revision과 서버 배선 조건을 검사해 그 사이의 서버 상태 변경을 거절합니다. 서버로 이미 보낸 요청 이후의 물리 분리를 소급 취소하지는 못합니다. 이미 발행된 수리 완료는 취소하지 않습니다.
