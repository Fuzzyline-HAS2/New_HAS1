# 발전기 배선 개수 절대값 동기화

발전기에서 확정한 **실제 연결 개수 0~4를 서버 `battery_pack`에 그대로 저장**합니다. `+1`/`-1` 누적 전송은 사용하지 않습니다. LG의 완료 기준이 3이어도 실제 4개가 연결되면 4를 저장하고, 4→3→2를 각각 구분합니다. `max_battery_pack`은 완료 여부를 판단하는 기준이며 전송값의 상한이 아닙니다.

## 입력과 완료 판단

- 충전 중과 완료 후 감시는 같은 상태기계를 사용합니다. 배선 네 개의 합계를 100ms마다 읽고, 같은 개수가 1초 동안 유지될 때 확정합니다. 개별 핀별 필터는 아닙니다.
- 샘플 사이 공백이 250ms를 넘으면 1초 안정 시간을 다시 시작합니다. 함수가 오래 멈춰 있었던 시간을 입력이 안정됐다는 증거로 사용하지 않습니다.
- `WireResetTracking()`은 즉시 원시 개수를 전송하거나 완료시키지 않습니다. 설정/대기/새 충전 사이클/기기 이름 변경에서 미확인 상태를 초기화합니다.
- 물리 확정값과 서버가 확인한 값은 분리합니다. 전송 실패 후 물리 입력이 바뀌지 않아도 다시 시도합니다. 이전에 쌓인 증감 이벤트를 순서대로 보내지 않고 재시도 시점의 최신 확정값만 보냅니다.
- 스타터 처리 전에 샘플링/동기화를 수행합니다. 입력 불안정, 기준 미달, 서버 확인 미완료이면 스타터 진행과 새로운 `BatteryFinish()`/`StartFinish()`를 보류합니다. 이미 수리 완료된 발전기를 되돌리지는 않습니다.
- 완료 안내 음원 뒤, 배터리 완료 요청 뒤, 실제 완료 함수 진입 직전에 GPIO를 다시 확인합니다. 긴 음원/통신 때문에 재안정화가 필요해도 같은 사이클의 안내 음원과 배터리 완료 요청을 반복하지 않습니다.
- 기존 서버 폴링의 `battery_pack` 값만으로 배터리 완료를 실행하던 경로와 상태 콜백 안의 보정 증감 전송은 제거했습니다. 실제 `activate` 복귀는 이전 전송 응답을 무시하는 가드에 삼켜지지 않습니다.

## 서버 계약

기존 `Send&column=battery_pack`는 다른 장치가 사용하므로 의미를 바꾸지 않습니다. 발전기는 같은 `/has2.php`에 전용 요청을 사용합니다.

```
GET ?request=GetGeneratorWires&mac=<MAC>&key=<device_name>
GET ?request=SetGeneratorWires&mac=<MAC>&key=<device_name>&value=<0..4>&epoch=<UUID>&revision=<expected>
```

문자열 쿼리 값은 URL 인코딩합니다. 성공 응답은 HTTP 200이고 다음 필드를 최상위 객체에 담습니다.

```json
{
  "success": true,
  "device_name": "LG",
  "battery_pack": 3,
  "epoch": "11111111-1111-1111-1111-111111111111",
  "revision": 8,
  "game_state": "activate",
  "device_state": "activate",
  "max_battery_pack": 3
}
```

- `epoch`은 길이 36인 UUID, `revision`은 0~4294967295의 JSON 정수입니다. 기기 이름·문자열 타입·숫자 타입을 검사하며 숫자 문자열/불리언/소수는 확인값으로 받지 않습니다.
- GET/409의 `battery_pack`은 과거 누적 오류를 교정할 수 있도록 signed int32 범위를 읽습니다. 실제 SET 성공 확인은 요청한 0~4와 완전히 일치해야 합니다. 완료 기준은 1~4만 유효합니다.
- SET은 현재 epoch/revision과 일치할 때만 반영됩니다. 성공 응답은 요청 epoch와 같고 revision이 요청값보다 커야 합니다. 동일 개수의 SET도 revision을 소비합니다.
- 충돌은 HTTP 409, `success:false`, `error:"CONFLICT"`와 동일 형태의 현재 스냅샷을 반환합니다. 400/403/404/5xx, 시간 초과, 잘못된 응답도 모두 미확인 상태로 남습니다. 증감 방식으로 돌아가는 fallback은 없습니다.
- 서버 revision이 상한에 도달하면 실패 처리하며 임의로 0으로 돌려 오래된 요청을 허용하지 않습니다.

처음 시작하거나 충전 사이클/기기 이름이 바뀌면 GET 후 동일 값이어도 CAS SET을 한 번 수행합니다. ESP 재부팅 전에 보낸 요청이 아직 서버에 지연되어 있을 수 있기 때문입니다. SET 타임아웃 뒤 GET 값이 이미 맞더라도 같은 CAS 확인이 필요합니다. 이때 새 revision을 확보하여 이전 지연 요청을 거절하게 합니다. 확인된 값이 유지되는 동안은 GET/SET을 반복하지 않습니다.

시도 사이에는 최소 2초를 둡니다. 한 시도 안에서 GET 후 SET을 연속 수행할 수 있습니다. 실패/충돌 후에는 GET으로 다시 문맥을 확인한 뒤 최신 확정값만 SET합니다. 일반 상태 변경은 CAS 문맥을 새로 조회하되 완료 음원이나 스타터 진행을 새 사이클로 초기화하지 않습니다.

전용 응답은 전체 장치 데이터가 아니므로 `my` 전체에 덮어쓰지 않습니다. 서버 epoch/상태가 달라지면 기존 `ReceiveMine()`과 `DataChanged()`로 전체 상태를 다시 적용합니다. 그 갱신이 실패하더라도 ACK를 확보하지 못한 채 완료를 진행하지 않습니다. 새 epoch를 받았다는 이유만으로 `repaired`/`repaired_all`을 다시 충전 단계로 돌리지 않습니다.

## 통신과 로그

`wire_http.ino`는 발전기 전용 `HTTPClient`를 매 요청마다 사용합니다. HAS2_Wifi의 공유 `http`를 재사용하거나 백그라운드에서 `my`를 읽고 쓰지 않습니다. 서버 주소는 `GENERATOR_SERVER_URL` 하나를 기존 HAS2_Wifi 생성자와 공유합니다. 외부 HAS2_Wifi 저장소/배포 의존성을 바꾸지 않습니다.

연결 제한 700ms, HTTP 읽기 제한 700ms를 지정하고, 응답 본문은 Content-Length가 있는 최대 1024바이트만 받습니다. 본문 수신 루프에는 별도 1초 제한을 둡니다. 이 제한들은 HTTP 전체 왕복의 엄격한 합산 deadline을 보장하지 않습니다. 현재 서버의 고정 길이 JSON 응답을 대상으로 하며 chunked/길이 없는 응답은 확인 실패로 처리합니다.

텔넷에 `[Wire] stable=...`, `[WireSync] confirmed=... revision=...`, HTTP 실패/재동기화 상태를 출력합니다. 모든 샘플을 로그로 쓰지는 않습니다. 별도의 PC 로그 수집기와 기존 텔넷 전송 경로는 변경하지 않습니다.

## 적용 순서와 한계

1. 서버에 새 GET/SET/CAS 계약과 테스트를 먼저 반영합니다.
2. 실제 서버의 endpoint 응답과 장치 MAC/이름 매핑을 확인합니다.
3. 그 다음 발전기 펌웨어를 빌드/배포합니다. 버전 증가는 기존 배포 워크플로를 사용합니다.
4. 현장에서 LG 3개 완료, 4→3→2, 빠른 연결/해제, 통신 복구, 설정/새 라운드, 수리 완료 후 배선 감시를 확인합니다.

새 서버 없이 새 펌웨어만 설치하면 수량 ACK를 얻지 못해 새 완료가 보류됩니다. 구형 서버로 되돌릴 때는 발전기 펌웨어의 전용 API 사용도 함께 고려해야 합니다. 이번 변경은 배포를 자동 실행하지 않습니다.

전기적 GND/전원 문제, Wi-Fi 또는 기존 HTTP/음원 함수의 블로킹 자체를 해결하지는 않습니다. 250ms 초과 공백이 1초 안에 반복되면 안정화가 끝나지 않는 것이 의도된 보수적 동작입니다. 따라서 실제 완료 시각은 '연결 후 정확히 1초'로 보장되지 않습니다. 새 수량 CAS 확인과 기존 `device_state=battery_max/repaired` 요청은 하나의 서버 트랜잭션이 아니므로 그 사이의 라운드 변경·물리 분리를 완전히 원자적으로 막지는 못합니다. 이미 발행된 수리 완료는 취소하지 않습니다.
