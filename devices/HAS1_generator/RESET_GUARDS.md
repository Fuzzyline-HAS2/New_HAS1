# 발전기 음원·HTTP·LED 정지 방지

배선 증가 시 안내음을 보내는 DFPlayer ACK 대기와 일반 HAS2_Wifi 응답 본문 수신을
수정한다. 배선의 8/10 판정, 100ms 측정 태스크, 대시보드 강제 완료 동작은 유지한다.

## 음원

레지스트리 DFRobotDFPlayerMini 1.0.6의 ACK 대기는 미소비 이벤트가 있으면 내부
`waitAvailable()`의 타임아웃을 거치지 않고 반복할 수 있었다. 수정 사본은 ACK를
기다리기 시작한 시각부터 전체 경과시간을 검사한다. 현재 발전기는 500ms를 사용한다.
호출 전 이벤트를 한 번 비우는 것만으로는 대기 중 도착하는 새 이벤트를 처리하지 못하므로,
실제 드라이버의 대기 루프를 수정한다. 재생 종료를 기다리는 상위 2초 제한과는 별개다.

`available()`는 호출마다 최대 10바이트만 처리하므로, 반환값이 false여도 UART에
읽을 데이터나 미완성 프레임이 남을 수 있다. 배선 완료 안내의 준비 단계는 이를
`hasPendingInput()`으로 별도 확인하고, 반복당 최대 8회 처리한다. 2초 안에
정리되지 않으면 부분 프레임 상태를 버리고 이번 안내를 생략해 게임을 계속한다.

태거와 순차 안내를 포함한 새 재생 명령도 송신 전에 남은 수신 데이터를 별도
500ms 기한으로 정리한다. 잡음이나 잘린 프레임이 계속되면 타임아웃 이벤트를
남기고 해당 재생을 생략한다. 한 재생 호출의 대기는 이전 ACK 500ms와 수신 정리
500ms를 합해 최대 약 1초이며, 이후 정상 입력에서 재생을 다시 시도할 수 있다.
이미 UART에 있던 이전 종료 이벤트를 새 음원 완료로 오인하지 않도록 하는 처리다.
DFPlayer 프로토콜에 명령 식별자가 없어 새 재생 송신 뒤 늦게 도착한 이전 종료
이벤트까지 완전히 구별하지는 못한다.

## HTTP 본문

발전기는 부팅 시 `EnableBoundedResponseBody()`를 호출한다. 일반 동기 요청의 성공·오류
응답 본문에 전체 1500ms 및 16KiB 제한을 적용하고, 불완전한 응답은 실패로 반환한다.
`HTTPClient::getString()` 내부에서 0바이트 읽기 타임아웃을 반복하는 경로를 피한다.
다른 장치는 이 설정을 켜지 않는 한 기존 경로를 사용한다.

이 제한은 **응답 본문 수신**에 대한 것이다. 연결·DNS·응답 헤더·Wi-Fi 재접속,
Google 크래시 로그 HTTPS 등 모든 호출에 하나의 절대 기한을 보장하는 변경은 아니다.
서버가 요청을 적용한 뒤 응답만 유실되는 경우까지 취소하거나 재전송 정책을 바꾸지 않는다.

## 빌드 및 검증

발전기 CI는 저장소의 `libraries/HAS2_Wifi`와 `libraries/DFRobotDFPlayerMini`를 사용한다.
로컬 빌드도 두 라이브러리를 명시해야 하며 `libraries/README.md`의 명령을 참고한다.

```sh
python3 devices/HAS1_generator/tests/run_dfplayer_tests.py
ARDUINOJSON_INCLUDE=/path/to/ArduinoJson/src python3 devices/HAS1_generator/tests/run_http_body_tests.py
ARDUINOJSON_INCLUDE=/path/to/ArduinoJson/src python3 devices/HAS1_generator/tests/run_wire_tests.py
```

호스트 테스트는 실제 드라이버/본문 리더에 제어된 응답과 가짜 시간을 제공한다.
실제 보드에서 발생한 리셋의 원인을 입증하거나 UART·Wi-Fi 전기 특성을 재현하지 않는다.
현장에서는 적용 버전 확인 후 배선 연결 안내음, 마지막 배선 완료, 해제 후 재연결,
대시보드 강제 완료를 확인하고 재발 시 `crash_log`의 리셋 사유와 마지막 위치를 수집한다.

## LED 전송 완료 대기

발전기의 네 곳 `pixels[].show()` 호출은 `NeoShow()`로 통합했다.
Adafruit의 색상 배열과 밝기 처리는 유지하고, 실제 전송만 발전기 전용
`generator_neopixel_tx.h`가 ESP-IDF RMT API로 수행한다. Arduino HAL의
이벤트 그룹 완료 알림 경로를 거치지 않는다. 전송 큐는 대기하지 않고,
각 스트립은 완료를 최대 100ms 기다린다. 현재 RGB 순서와 10MHz 기준
0비트 4/8틱, 1비트 8/4틱을 유지하며 프레임 전후에 300us LOW를 보낸다.

초기화·전송·완료 대기가 실패하면 해당 스트립만 재부팅까지 출력을 중단한다.
실패한 스트립 번호와 오류 코드는 한 번만 로그에 남긴다. 나머지 스트립과
게임/통신 처리는 계속 진행한다. 자동 복구나 실패한 프레임 재전송은 하지 않는다.
전송 데이터와 인코더/채널은 정적 수명으로 유지하고 실패 이후 덮어쓰거나
해제하지 않는다. 지연된 인터럽트가 도착해도 해당 스트립을 다시 사용하지 않는다.

현재 classic ESP32의 IDF 5.5.5 `rmt_disable()`은 실행 중인 전송을 중단할 때
TX_DONE을 제한 없이 확인하는 경로가 있으므로, 시간 초과 뒤 이 API로
정리하지 않는다. 초기화도 스트립마다 부팅 중 한 번만 시도하여 반복 할당을
방지한다. LED 핀에 대해 초기화 이후 `pinMode`, `digitalWrite`, 기존 `show()`를
추가하지 않아야 한다. 렌더링은 기존처럼 setup/메인 루프에서만 호출한다.

호스트 장애 주입 검증은 완료 알림 누락/지연, 큐 실패, 부분 초기화 실패,
전송 중 버퍼 유지, 다른 스트립의 정상 동작 및 신호 인코딩을 확인한다.
실제 발전기에서 알림 유실이 발생했다는 증거나 전기적 리셋 해결을 보장하지는 않는다.
보드에서는 4개 스트립 색상·밝기·빠른 연속 갱신과 연결/해제 동작을 확인한다.
