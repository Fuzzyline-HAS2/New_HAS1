# 발전기 장기 Wi-Fi 오프라인 복구

## 해결하는 문제

v30의 네트워크 작업은 연결 실패를 정상적으로 반환할 때마다 태스크 워치독을 갱신한다. 이는 작업이 멎은 상태와 다르므로 기존 워치독은 수 분 이상 Wi-Fi에 연결되지 않아도 재부팅하지 않는다. 이 수정은 `WiFi.status() != WL_CONNECTED`가 연속되는 시간을 장치 전용 정책으로 감시한다. HTTP 오류, 서버 응답 없음, HTTP 4xx/5xx만으로 재부팅하지 않는다.

이 Wi-Fi 복구 정책은 공용 HAS2_Wifi 라이브러리, OTA 구조, 펌웨어 버전을 변경하지 않는다. 완료 HTTP 계약은 [조건부 완료 복구](COMPLETION_RECOVERY.md)를 따른다. 무선 드라이버의 scan 버퍼나 worker 태스크를 강제로 해제하지 않는다. 이미 존재하는 worker 정지/scan driver fault 워치독 경로도 유지한다.

## 시간과 복구 범위

| 직전 연속 복구 재시작 횟수 | 이번 부팅의 연결 이력 | 연속 오프라인 임계시간 |
|---|---|---|
| 0 | 연결을 한 번 이상 관측한 뒤 끊김 | 30초 + 기기별 0~5초 |
| 0 | 아직 한 번도 연결되지 않음 | 180초 + 기기별 0~5초 |
| 1 | 무관 | 300초 + 기기별 0~5초 |
| 2 | 무관 | 900초 + 기기별 0~5초 |
| 3 이상 | 무관 | 1,800초 + 기기별 0~5초 |

사용 중 끊긴 장치는 글러브와 같이 30초를 기준으로 빠르게 복구한다. 부팅부터 연결되지 않은 장치는 초기 Wi-Fi 연결에 180초를 허용한다. 연결 이력은 메인이 현재 `WiFi.status()`로 관측한 값이며 서버의 게임 상태와 무관하다. 이 이력은 RTC에 저장하지 않고 매 부팅 초기화한다. 단, 자체 복구 재시작이 반복되면 위 5/15/30분 backoff가 우선한다.

MAC 문자열의 해시를 지터로 사용하므로 AP 전체 장애 때 장치가 같은 시각에 모두 재부팅하는 위험을 낮춘다(충돌 가능). 첫 복구를 크게 늦추지 않도록 지터는 최대 5초다. 이후에도 30분 간격의 느린 재시도를 허용해 횟수 소진 후 영구 차단되지는 않는다. 이 값들은 운영 정책이며 전파 환경에서 검증된 복구 보장시간은 아니다.

재시작 이전에 이미 오프라인이었던 시간은 다음 부팅의 타이머에 더하지 않는다. 부팅 및 게임 초기화 시간은 위 임계시간에 포함되지 않으므로 실제 재시작 간격은 더 길 수 있다. 연결이 잠시라도 복구되면 연속 오프라인 시간은 다시 측정한다. 재시작 횟수는 Wi-Fi가 연결되어 있고 최근 15초 이내 유효한 Loop/ReceiveMine 또는 조건부 완료·확인 응답이 있는 상태를 10분 동안 유지해야 초기화된다.

횟수·오프라인 시간·요청 표식·체크값은 초기화 생성자가 없는 RTC NOINIT POD에 저장한다. `ESP_RST_SW`이고 유효한 자체 재시작 요청 표식이 있을 때만 이전 횟수를 보존한다. 표식은 부팅 때 소비한다. 전원 재인가, 브라운아웃, 무관한 재부팅, 체크값 불일치는 이 이력을 초기화한다. RTC는 전원이 끊겨도 남는 저장소가 아니며, 체크값은 보안 서명이 아니다.

## 재시작 안전 조건

- OTA 유지보수 중에는 이 자동 재시작을 보류한다. 기존 오프라인 OTA 유지보수 취소(10초)는 그대로 적용된다.
- 미확정 완료가 전용 NVS에 저장·검증되어 있으면 재시작 후 원래 epoch/revision으로 복원할 수 있으므로 재시작을 허용한다. 복원 가능한 기록이 없는 미확정 완료는 기존처럼 재시작을 보류한다.
- 확실히 미전송된 완료 요청 또는 아직 대기열에만 있는 요청은 실행 중 요청이 없으면 재시작할 수 있다. 재시작은 이 메모리 대기열을 폐기하며 기존 부팅 절차가 서버 상태를 새로 읽는다.
- 실행 중 HTTP 요청, 미처리 결과 mailbox, worker 생성 실패/driver fault도 보류한다. 실제 worker 정지는 기존 워치독이 담당한다.
- 메인과 worker가 공유하는 mutex 안에서 재시작 fence를 세운다. 새 요청 enqueue, worker 선택, 최종 HTTP dispatch 모두 이 fence를 확인한다.
- fence 뒤에 현재 `WiFi.status()`를 다시 읽는다. 그사이 연결됐다면 fence를 해제하고 재시작하지 않는다.
- 재시작 직전 동기 플래시 쓰기나 MQTT 전송 완료 대기를 추가하지 않는다.

## 로그

BlackBox 이벤트 종류 `Recovery`, label `wifi.offline.recovery`:

| 필드 | 의미 |
|---|---|
| value1 | stage: 1 오프라인 시작, 2 재시작 보류, 3 재시작 요청, 4 정상 유지 후 backoff 초기화, 5 다음 부팅에서 확인한 이전 자체 재시작 요청 |
| value2 | 연속 오프라인 경과 ms |
| value3 | 사용한 재시작 횟수(최대 65535) |
| detail | stage 1이면 적용 임계시간 ms, stage 2이면 보류 비트, 그 외 0 |

보류 비트: `1=OTA`, `2=uncertain_completion`, `4=worker_fault`, `8=in_flight`. 동일 보류 이유는 30초에 한 번으로 제한하며 이유가 바뀌면 즉시 기록한다. 여러 이유의 비트를 합칠 수 있다.

즉시 재시작하면서 마지막 BlackBox 큐 데이터가 플래시에 저장되지 않을 수 있다. 다음 부팅에서 RTC 요청 기록을 stage 5로 다시 발행한다. 이는 재시작 **요청 이력**이며 실제 리셋 이유는 별도 `device.boot`의 `esp_reset_reason()`으로 확인한다. stage 3만 보이고 stage 5가 없다면 전원 손실/RTC 유효성 등도 고려해야 한다. 서버 장애만 발생하면 이 Wi-Fi 오프라인 복구 이벤트는 나오지 않을 수 있다.

## 검증

- `tests/run_offline_recovery_tests.py`: 기연결 후 30초/최초 연결 180초 구분, 재연결 후 재단절, 부팅 시 연결 이력 초기화, 증가·장기 재시도, 최대 5초 지터, RTC 소비/유효성, POD 생성자 부재, 정상 연결/서버 안정기간, millis rollover, 카운터 포화.
- `tests/run_network_tests.py`: 실제 `network.ino`를 컴파일한 제어 스케줄 harness. 기존 게임·완료 확인·OTA 회귀에 더해 정상 반환하는 장기 오프라인, HTTP 503 장기 장애 제외, OTA/worker/active/mailbox 보호, 저장된 불확실 완료의 재시작 허용과 미저장 상태 보호, 현재 연결 재확인, enqueue/선택/최종 dispatch fence 검증.
- 기존 connection, diagnostics, boot network, BlackBox LED contention, timer boot 검사 유지.

호스트 테스트는 실제 FreeRTOS 스케줄·Wi-Fi 드라이버·전원 문제를 재현하지 않는다. 배포 전에 시험 기기에서 AP 단절→재시작→복귀, AP 장기 정지 시 backoff, 서버만 정지 시 재시작 없음, OTA 중 보류, 충전/수리 응답 유실 후 중복 처리 없음, 로그 stage 3→5와 boot reason 연결을 확인해야 한다. 한 대에서 먼저 검증하며 현장 OTA 배포는 별도 단계다.
