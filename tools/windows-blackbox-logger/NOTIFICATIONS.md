# Slack·Notion 장애 알림 설정

이 기능은 기본 비활성화입니다. Windows 수집기의 사건 관리와 별도 알림 작업자가 실행하며, 장치 MQTT 저장·ACK 경로에서는 외부 HTTP 요청을 하지 않습니다. 게임 중 참가 글러브의 서버 통신 중단 사건을 사용합니다. MQTT 로그가 잠시 없거나 게임 종료 후 배터리를 교체했다는 이유로 알림을 만들지 않습니다. 서버 사건 수집을 먼저 설정하고 실제 로그 유입을 확인하세요.

## 준비

- Slack: 채널 이름은 `#has1-device-alerts`, 앱 이름은 `HAS1 BlackBox`를 권장합니다. 두 방식 중 하나를 사용합니다.
  - **Bot 토큰(권장)**: 앱의 Bot Token Scopes에 `chat:write`만 추가하고 워크스페이스에 설치한 뒤 `xoxb-`로 시작하는 Bot User OAuth Token을 받습니다. 채널에서 `/invite @HAS1 BlackBox`로 앱을 초대하고, 채널 정보 하단의 **채널 ID**(`C`로 시작)를 확인합니다(1호점 `#has1-device-alerts`는 `C0CBYRUAH6Y`). PagerDuty·Opsgenie처럼 **장애 1건(= 문제가 생긴 게임 세션)에 카드 1개**를 올리고 상태가 바뀔 때마다 그 카드를 고칩니다. 아래 "Slack 장애 카드"를 참고하세요.
  - **Incoming Webhook**: 이 채널에 Webhook을 발급합니다. URL 자체가 암호입니다. 메시지 ID가 돌아오지 않아 복구 알림은 별도 메시지로 올라옵니다.
- Notion: `HAS1 장애 관리` 페이지 아래 세 DB를 씁니다. 업계 표준(ITIL·Jira Service Management)의 Alert → Incident → Problem 구조이며, 장애 단위는 게임 세션 1판입니다. 내부 연결 이름은 `HAS1 BlackBox Logger`를 권장하고, **`HAS1 장애 관리` 페이지**의 연결 메뉴에서 이 연결을 추가해 아래 DB 전체에 읽기·추가·수정 권한을 줍니다. API 버전 `2025-09-03`의 데이터 소스 API를 사용하므로 database ID와 data source ID를 혼동하면 안 됩니다.

| DB | 쓰는 주체 | 내용 |
| --- | --- | --- |
| `HAS1 장치 이벤트` | 수집기 | 장치 끊김 1건 = 1행. 끊김부터 복구(또는 감시 종료)까지 같은 행을 갱신 |
| `HAS1 장애 (게임 세션)` | 수집기가 생성, 사람이 관리 | 게임 세션 1판 = 1행. 그 판의 장치 이벤트가 연결됨 |
| `HAS1 문제 (근본 원인)` | 사람 | 원인이 같은 장애를 묶고 조치·재발을 추적. 수집기는 쓰지 않음 |

수집기 설정에는 **`HAS1 장치 이벤트`의 data source ID**만 넣습니다. 장애 DB는 이벤트 DB의 `게임 세션` 관계 속성이 가리키는 데이터 소스를 따라가 찾습니다. 수집기는 스키마를 자동 변경하지 않으므로 아래 속성은 정확한 이름과 유형으로 유지해야 합니다. 표에 없는 속성(심각도·롤업·담당자 등)은 자유롭게 추가·변경할 수 있습니다.

| DB | 속성 | Notion 유형 |
| --- | --- | --- |
| 장치 이벤트 | 이벤트 | 제목(title) |
| 장치 이벤트 | 사건 ID · MAC · 요약 | 텍스트(rich_text) |
| 장치 이벤트 | 상태 | 상태(status) |
| 장치 이벤트 | 게임 세션 | 관계(relation) → 장애 DB |
| 장치 이벤트 | 장치 · 역할 · 매장 · 종료 사유 | 선택(select) |
| 장치 이벤트 | 발생 시각 · 종료 시각 | 날짜(date) |
| 장치 이벤트 | 지속(초) | 숫자(number) |
| 장애 | 장애 | 제목(title) |
| 장애 | 세션 키 · 게임 세션 ID | 텍스트(rich_text) |
| 장애 | 매장 | 선택(select) |
| 장애 | 처음 발생 | 날짜(date) |

선택 속성의 새 값(새 장치 이름 등)은 Notion이 옵션을 자동으로 만듭니다. 쉼표는 선택 옵션에 쓸 수 없어 공백으로 바꿉니다. `상태`는 아래 옵션이 **이미 존재해야** 하며 공백까지 정확히 일치해야 합니다. 수집기는 상태 옵션을 만들지 않습니다.

| 사건 원본 상태 | Notion 상태 옵션 | 의미 |
| --- | --- | --- |
| `offline` | `장애중` | 통신 장애 발생, 아직 복구 안 됨 |
| `recovered` | `복구됨` | 서버에서 통신 복구 확인 |
| `monitoring_ended` | `미복구 종료` | 복구 확인 전 게임이 끝나 감시 종료, 별도 확인 필요 |

감시 종료는 복구가 아니므로 `복구됨`으로 표시하지 않습니다. Notion 날짜는 분 단위로 저장되므로, 수집기가 원본 시각으로 `지속(초)`를 계산해 기록합니다. 장애 DB의 `심각도`는 Notion 수식으로 계산합니다. `영향`이 `게임 중단·환불`이면 SEV1, `진행 지장`이거나 `미복구 종료` 이벤트가 있으면 SEV2, 나머지는 SEV3입니다.

설정 시와 매 전달 작업 전에 이벤트 DB의 속성·상태 옵션을 검증합니다. 새 이벤트를 만들 때는 장애 DB의 속성도 검증합니다. 누락된 속성·유형 불일치·옵션 불일치는 쓰기 전에 중단하며, 원격 오류 본문을 포함하지 않는 오류 코드만 남깁니다. 토큰이나 Webhook URL은 채팅에 보내지 말고 현장 설정의 숨김 입력창을 사용하세요.

`사건 ID`로 기존 이벤트를 조회해 사건당 한 행을 만들고 상태 변경 시 갱신합니다. 복구·감시 종료 갱신은 처음 전달에서 받은 페이지 ID를 대기열에 함께 저장해 조회 없이 그 행을 바로 수정합니다. Notion 조회는 방금 만든 행을 곧바로 보여 주지 않을 수 있기 때문입니다. 갱신할 때는 게임 세션 연결을 건드리지 않습니다. 중복된 사건 ID 행이 이미 있으면 임의 선택하지 않고 오류로 남깁니다.

새 이벤트는 `세션 키`(`매장/게임 세션 ID`)로 장애 행을 찾아 연결하고, 없으면 먼저 장애 행을 만듭니다. 같은 세션의 장치가 한꺼번에 끊기면 이벤트가 연달아 전달되므로, 한 번 찾거나 만든 장애 행은 수집기가 실행되는 동안 기억해 다시 조회하지 않습니다. 장애 행 생성 응답이 유실되면 재시도 때 다시 조회한 뒤 만듭니다. 그래서 최악의 경우에도 빈 장애 행이 하나 더 생길 뿐 이벤트가 중복되거나 빠지지 않습니다. 같은 세션 키 행이 여러 개면 가장 먼저 만들어진 행(같은 분이면 페이지 ID가 작은 행)에 연결합니다. 장애 행을 만든 뒤 이벤트 생성이 권한 오류 등으로 영구 실패하면 이벤트 없는 장애 행이 남을 수 있습니다. 세션 키는 게임 서버의 세션 ID가 매장 안에서 재사용되지 않는다는 전제입니다.

새 이벤트는 최대 6번의 API 호출이 필요합니다. 이벤트 생성 직전에 HTTP 예산이 5초 미만으로 남았으면 아무것도 보내지 않고 재시도합니다. 예산이 끊긴 생성 요청은 결과를 알 수 없어 수동 확인 대상이 되기 때문입니다. Notion의 409(`conflict_error`)는 재시도합니다. 여러 수집기가 같은 데이터 소스에 동시에 같은 사건을 쓰지 않도록 운영하세요. Notion은 이 속성들에 고유 제약을 보장하지 않습니다.

### 블랙박스 증거 요약

복구·감시 종료로 끝난 이벤트에는 그 이벤트 페이지 본문에 `📦 블랙박스 증거 (후보 · 원인 미확정)` 표를 한 번 붙입니다. 원본은 매장 PC SQLite에 남기고 사람이 읽는 요약만 올립니다. 장애 기록에는 요약과 원본 위치를, 원본은 로그 저장소에 두는 장애 관리 도구의 일반적인 방식입니다.

| 출처 | 고르는 기준 | 시각 표시 |
| --- | --- | --- |
| 게임 서버 | 같은 사건 ID의 끊김 감지·재연결·감시 종료(전후 60초) | 한국 시각 |
| Omada | 같은 MAC의 AP 접속·해제·로밍·접속 실패(전후 60초). IP·포트가 담긴 트래픽 기록은 제외 | 한국 시각 |
| 장치 블랙박스 | 끊기기 전 마지막으로 올라온 기록 앞 5건과 그 뒤로 기록된 것(끊긴 동안과 재연결 직후, 최대 200건을 읽음) | 표 안의 부팅 순번(1, 2, …) · 켜진 뒤 경과 시간(수신 시각) |

- 장갑은 끊긴 동안의 기록을 재연결 뒤에 올립니다. 이 업로드는 서버의 복구 판정보다 먼저 올 수도 있습니다. 그래서 끊긴 뒤 같은 MAC의 기록이 처음 들어온 때와 이벤트가 끝난 때 양쪽에서 모두 2분이 지나면 붙입니다. 장치 기록이 아직 없으면 1분마다 다시 확인하므로, 보통 복구 2~3분 뒤에 표가 붙습니다. 6시간 안에 장치 기록이 오지 않으면 서버·Omada 기록만으로 붙이고 "장치 기록이 아직 올라오지 않았습니다"라고 표시합니다. 기다리는 동안은 외부 요청을 보내지 않으며 재시도 횟수에도 들어가지 않습니다. 요약을 만드는 중 오류가 나도 보낸 것이 없으므로 1분 뒤 다시 만들고, 이벤트가 끝나고 7시간이 지나도 실패하면 `evidence_build_failed` 영구 오류로 남깁니다.
- Omada 기록이 10건을 넘으면(접속·해제 반복) 처음 5건과 마지막 5건만 보이고 "일부만 표시했습니다"라고 적습니다.
- 장치 기록에는 실제 시각이 없습니다. 업로드 시각으로 발생 시각을 추정하지 않고, 기록 순서(seq)로 끊김 전후를 고릅니다. 와이파이 끊김 원인 코드(예: `200 BEACON_TIMEOUT`)와 주요 값은 읽기 쉬운 이름으로 바꿉니다.
- 게임 중 수백 ms마다 반복되는 진동·LED 출력 기록(`motor.applied`·`output.applied`·`motor.suppressed`)은 연속된 구간마다 "모터·LED 출력 변경 N건" 한 줄로 묶습니다.
- 부팅 ID는 부팅마다 임의 값이라 표에서는 나온 순서대로 1, 2로 보여 줍니다. 부팅이 바뀌는 곳에는 `🔁 재부팅 (부팅 1 → 2) · 리셋 원인 1 POWERON 전원 켜짐`처럼 한 줄을 넣습니다. 리셋 원인은 장갑이 기록한 ESP-IDF `esp_reset_reason()` 값입니다(예: 4 PANIC 크래시, 6 TASK_WDT 워치독, 9 BROWNOUT 전압 저하). 대시보드의 장갑 리셋도 재부팅으로 나오므로 게임 기록과 함께 확인하세요.
- 표는 최대 40줄입니다. 넘치면 일반 기록부터 빼고 부팅·크래시·와이파이·복구 기록과 재부팅 표시는 남긴 뒤 "일부만 표시했습니다"라고 적습니다. 이 중요 기록은 따로 조회하므로 출력 기록이 수백 건 쌓여도 읽기 한도(200건)에 밀려 빠지지 않습니다. 중요 기록만으로도 넘치면(재접속 시도 반복 등) 처음과 끝을 절반씩 남깁니다. 전체는 매장 PC에서 `incidents.py --incident-id`로 내보냅니다.
- 붙이기 전에 페이지 본문 앞부분에 이 제목이 이미 있는지 확인합니다. 그래서 응답이 유실되어 다시 시도해도 표가 두 번 붙지 않습니다. 이 확인은 본문 첫 100개 블록만 봅니다.
- 표는 원인 판단이 아니라 후보 기록입니다. 원인은 사람이 `HAS1 문제 (근본 원인)` DB에 적습니다.

붙을 표는 매장 PC에서 미리 볼 수 있습니다(읽기 전용).

```powershell
.\.venv\Scripts\python.exe incidents.py --database "$env:ProgramData\HAS1BlackBox\data\incidents.sqlite3" --telemetry-database "$env:ProgramData\HAS1BlackBox\data\telemetry.sqlite3" --evidence-summary '사건ID'
```

### Slack 장애 카드 (bot 토큰 방식)

노션의 장애 단위와 같게, 문제가 생긴 게임 세션마다 카드 하나를 씁니다. 같은 판에서 장갑 여러 개가 함께 끊기면 원인이 같은 경우가 많아서, 장갑마다 글을 따로 올리지 않고 한 카드와 한 스레드에서 대응합니다.

```text
🔴 장애 진행 중 1건 · 세션 1657 · store-1      ← 첫 끊김 때 올라오고(채널 알림 1번) 이후엔 수정만
매장 store-1   게임 세션 1657   처음 끊김 10/25 07:25:29
장애 2건 (복구 1 · 미복구 0 · 진행 중 1)   심각도 SEV3 · 자동 판정
🔴 G1P1 · 10/25 07:25:29 끊김 → 장애중
🟢 G1P5 · 10/25 07:25:29 끊김 → 18초 만에 복구
📒 노션 장애 페이지 · 원인은 아직 확정되지 않았습니다. 장치별 경과는 스레드에 있습니다.
  └ 스레드: 사람이 원인·조치를 정리하는 곳. 봇은 미복구 종료만 남김
```

- 카드 제목은 진행 중 장애가 있으면 🔴, 모두 끝났는데 미복구가 있으면 🟠, 모두 복구되면 🟢입니다. 심각도는 노션 장애 DB와 같은 자동 규칙(미복구 있음 SEV2, 그 외 SEV3)이고, SEV1(게임 중단·환불)은 사람이 노션에서 정합니다.
- 장갑이 끊기거나 복구될 때마다 카드를 고칩니다. 메시지 수정은 알림이 가지 않으므로 채널 알림은 카드가 처음 올라올 때 한 번입니다. 같은 판에서 함께 끊긴 장갑은 카드 수정으로만 반영합니다.
- 사람이 봐야 하는 두 경우는 스레드에 답글을 달고 채널에도 함께 보여 줍니다(`reply_broadcast`). 하나는 복구 확인 없이 게임이 끝난 장갑(`미복구 종료`)이고, 다른 하나는 카드의 장애가 모두 끝난 뒤 새로 끊긴 장갑입니다. 답글에는 노션 장치 이벤트 링크가 붙습니다.
- 장갑의 블랙박스 표가 노션 이벤트 페이지에 붙으면 카드 스레드에 조용한 답글(채널 알림 없음)로 링크와 핵심 한 줄을 남깁니다. 예: `📦 G2P1 블랙박스 기록 · 재부팅 1번(리셋 원인 1 POWERON 전원 켜짐) · 와이파이 끊김 원인 202 AUTH_FAIL · 📒 노션 블랙박스 표`. 기록에 해당 내용이 없으면 `재부팅·와이파이 끊김·크래시 기록 없음`, 장치 기록이 끝내 오지 않으면 `장치 기록 아직 없음`으로 적습니다. Slack 카드에 알린 장갑에만 답니다.
- 카드에는 Slack에 이미 알린 장애만 셉니다(알림이 취소된 장애는 넣지 않음). 줄은 진행 중 장애를 먼저, 그다음 최신 순으로 최대 12줄을 보이고, 건수는 그 판 전체로 셉니다.
- bot 방식에서는 노션 장애 페이지 링크를 붙이기 위해 노션 전달을 Slack보다 먼저 처리합니다. 그래서 Slack 카드가 노션 전송 시간(보통 수 초, 최대 약 10초)만큼 늦을 수 있습니다. 노션이 실패해 재시도 대기 중이면 Slack은 기다리지 않고, 링크는 다음 수정 때 붙습니다. Webhook 방식은 순서와 동작이 예전과 같습니다.
- 이 기능을 배포할 때 열려 있던 장애의 기존 장갑별 카드는 다음 갱신 때 게임 세션 카드로 이어받습니다.
- 카드의 메시지 ID와 노션 장애 페이지 ID는 사건 DB `session_links`에 게임 세션별로 저장합니다. 카드가 삭제되었으면 새 카드를 올리고 이후에는 그 카드를 씁니다. 새 카드를 올린 응답이 유실되면(결과 불명) 같은 판의 다음 장애 때 카드가 하나 더 생길 수 있습니다.
- 링크 외의 모든 값(장치 이름 등)은 plain text라 `@channel` 같은 멘션이 되지 않습니다. mrkdwn은 수집기가 UUID로 만든 노션 링크에만 씁니다.

### 발전기 끊김·재부팅 (수집기 자체 판정)

게임 서버는 장갑 끊김만 감시합니다. 발전기는 수집기가 이미 받는 기록으로 직접 판정하며, 게임 서버(Core OS)는 바꾸지 않습니다. `telemetry.incidents.generators`로 켭니다(기본 꺼짐).

```json
"generators": {"enabled": true, "devices": {"BG": "A4:F0:0F:D9:0B:CC", "LG": "A4:F0:0F:D9:06:BC"}}
```

- **무응답**: 발전기는 게임과 무관하게 2초마다 서버에 `Loop`를 요청합니다(실패 시 최대 약 8초 간격). 게임 중에 20초(`silence_seconds`) 넘게 요청이 없으면 장갑과 같은 `🔴 연결 끊김`으로 알리고, 다시 요청하면 복구, 게임이 끝나면 미복구 종료로 닫습니다. 역할은 `generator`로 표시합니다.
- 기준 시계는 "어느 장치든 가장 최근 요청 시각"입니다. 서버나 서버 로그가 멈춰 모든 장치가 5초 넘게 조용하면 시계도 멈추고, 재개된 시점부터 다시 셉니다. 그래서 서버 재시작·멈춤은 발전기 경보가 되지 않습니다. 게임 시작 전부터 끊겨 있던 발전기는 게임 시작부터 셉니다.
- 발전기 3대(`group_min`) 이상이 10초(무응답 기준의 절반을 넘지 않음) 안에 함께 끊기면 `발전기 BG·LG·SG` 한 건으로 묶습니다(공통 원인, 예: 발전기 전체의 와이파이 재접속). 모두 다시 요청해야 복구로 닫고, 그사이 먼저 돌아온 발전기가 다시 끊기면 따로 알립니다. 그룹에는 장치 하나의 MAC이 없어 블랙박스 표를 붙이지 않습니다.
- 카드의 "마지막 수신"은 그 발전기의 실제 마지막 요청입니다. 게임 시작 전부터 끊겨 있던 발전기는 비어 있을 수 있습니다. 게임마다 의도적으로 꺼 두는 발전기가 있으면 매 게임 20초 뒤 알림이 갑니다. 그런 장치는 `devices`에서 뺍니다.
- **재부팅**: 발전기 블랙박스의 부팅 기록이 panic·워치독·전압 저하·전원 글리치·CPU 잠김이면 게임 여부와 상관없이, 전원 투입·외부 리셋이면 게임 중일 때만 `🔁 장치 재부팅`으로 알립니다. 소프트웨어 재시작(OTA·자체 복구)은 알리지 않습니다. 이미 끝난 일이라 한 번만 알리고 노션에는 `복구됨`·종료 사유 `재부팅 패닉(크래시)` 등으로 남기며, 이벤트 페이지에 그 부팅 기록 직전부터의 블랙박스 표(크래시 기록 포함)를 붙입니다. Slack에서는 스레드 답글과 채널 표시로 알립니다.
- 재부팅 판정에는 장치 기록 가져오기(`device_import.enabled`)가 켜져 있어야 합니다. 무응답 판정은 서버 기록만으로 동작합니다.
- 게임 밖 재부팅은 하루 단위 세션 `게임외-YYYYMMDD`(한국 날짜)에 모읍니다. 같은 발전기는 같은 세션(게임 또는 게임외 하루) 안에서 10분에 한 번만 알립니다(와이파이가 끊긴 동안 크래시가 반복되면 부팅 기록이 한꺼번에 올라오므로). 묶여서 알리지 않은 재부팅은 사건 목록에 남지 않으며, 표를 만들 때(약 2분 뒤)까지 올라온 기록이면 그 알림의 블랙박스 표(최대 40줄)에 보입니다.
- 장치 기록의 시각은 수집기가 받은 시각입니다. 수집기가 받은 지 5분 넘게 지나 처리되는 부팅 기록(옛 기록을 다시 읽은 경우)은 알리지 않고, 서버 상태 확인이 끊겨 1시간 넘게 보내지 못한 재부팅 알림은 버립니다. 장치가 오래 오프라인이었다가 늦게 올린 부팅 기록은 받은 시점에 알립니다.
- 판정만 재생해 보려면(읽기 전용): `generator_watch.py --telemetry-database <telemetry.sqlite3> --device BG=<MAC> ...` 재생은 위 시간 제한과 10분 묶음을 적용하지 않는 판정 기준 확인용입니다. 2026-10-24 기록 재생 결과 게임 12판 동안 무응답 경보 0건, 게임 밖 panic 재부팅 15건(펌웨어 v33·v34)이었습니다.

## Windows에서 활성화

1호점 설치 대상과 순서는 [STORE1-HANDOFF.md](STORE1-HANDOFF.md)에 정리되어 있습니다.

수집기를 설치하고 [README의 사건 수집 활성화 절차](README.md#서버-로그사건-수집-활성화)에 따라 실제 `%ProgramData%\HAS1BlackBox\config.json`의 서버 로그 입력과 사건 기능을 먼저 활성화합니다. `telemetry.incidents.database`는 `data/incidents.sqlite3` 또는 해당 ProgramData 폴더의 절대 경로로 지정해야 LocalService가 쓰기 가능한 데이터 폴더를 사용합니다. 관리자 PowerShell에서 설치 폴더의 다음 스크립트를 실행합니다.

```powershell
# Slack bot 토큰 방식(게임 세션별 장애 카드). 채널 ID는 비밀이 아닙니다.
.\configure-notifications.ps1 -EnableSlack -SlackChannelId 'C0CBYRUAH6Y'
# Slack Incoming Webhook 방식:
.\configure-notifications.ps1 -EnableSlack
# 또는 Slack과 Notion을 함께 사용(DB 페이지의 복사한 링크):
.\configure-notifications.ps1 -EnableSlack -EnableNotion -NotionDatabaseUrl 'https://www.notion.so/복사한DB링크'
# 이미 데이터 소스 ID를 아는 경우 URL 대신 지정:
.\configure-notifications.ps1 -EnableSlack -EnableNotion -NotionDataSourceId '데이터-소스-UUID'
Restart-Service HAS1BlackBoxCollector
```

Slack bot 토큰·Webhook URL과 Notion 토큰은 숨김 입력창에서 입력합니다. `-SlackChannelId`를 지정하면 Webhook 대신 bot 토큰을 묻습니다. 다른 채널 옵션과 함께 쓸 때도 그대로 붙이면 됩니다. 명령줄 인수·환경변수·JSON 설정 파일에 직접 쓰지 않습니다. 스크립트는 Windows DPAPI(LocalMachine)로 암호화한 새 `notifications-*.dpapi` 파일을 만들며, ACL을 SYSTEM·관리자 전체 접근 및 LocalService 읽기로 제한합니다. 이 파일은 같은 Windows PC에서만 복호화됩니다. 새로 설정할 때 선택한 채널만 활성화되므로 기존 두 채널을 유지하려면 두 옵션을 모두 지정하세요. 이전 암호 파일은 자동 삭제하지 않으므로 정상 동작 확인 후 현재 `credential_file`에 지정되지 않은 파일만 삭제할 수 있습니다.

설정 위치는 다음과 같습니다. 실제 ID 이외의 비밀은 포함하지 않습니다.

```json
{
  "telemetry": {
    "incidents": {
      "enabled": true,
      "database": "data/incidents.sqlite3",
      "notifications": {
        "enabled": true,
        "credential_file": "notifications-생성된파일명.dpapi",
        "slack": {"enabled": true, "channel_id": "C0123456789"},
        "notion": {"enabled": true, "data_source_id": "12345678-1234-1234-1234-123456789abc"}
      }
    }
  }
}
```

위 조각으로 전체 설정 파일을 덮어쓰지 마세요. 설정 스크립트가 기존 설정에 병합합니다. `-NotionDatabaseUrl`을 사용하면 공식 Notion API에 읽기 전용 GET 요청을 보내 데이터 소스 ID를 확인합니다. 하나일 때만 자동 선택하며, 여러 개면 명시적 선택을 요청합니다. `notion.so`·`www.notion.so`·`app.notion.com`의 복사한 DB 링크를 지원하며, 입력한 링크로 직접 접속하지 않고 ID만 추출합니다. URL이나 데이터 소스 ID 중 어느 방식이든 저장 전에 읽기 전용 스키마 검증을 수행합니다. 검증에 실패하면 기존 알림 설정을 유지합니다. 설정 도구는 공통 실패 안내를 표시합니다. 실행 중 발송 대기열에 남는 오류 코드에서 `notion_schema_mismatch`는 필드 이름·유형, `notion_status_options_mismatch`는 위 상태 옵션 이름을 확인해야 한다는 뜻입니다. `http_401`·`http_403`·`http_404`는 토큰과 대상 DB 접근 권한을 확인하세요. 설정 시에는 외부 테스트 메시지나 Notion 기록을 만들지 않습니다. 최초 연결 검증은 운영 승인된 시험 사건으로 진행하고 전송 대기 상태를 확인합니다. 실제 Slack·Notion 계정으로의 전송은 현장 설정 후 검증해야 합니다.

## 전달 보장과 실패 처리

- Slack 알림은 매장·장치·MAC·한국 시각·무응답/장애 지속 시간을 담은 카드입니다. 값이 없거나 `unknown`인 항목은 표시하지 않습니다. 본문은 plain text라 장치/서버 문자열이 `@channel` 같은 멘션 명령이 되지 않습니다.
- Bot 토큰 방식은 게임 세션 카드를 먼저 수정하고(`chat.update`, 재시도 안전), 미복구 종료일 때만 그 뒤에 스레드 답글을 보냅니다(`chat.postMessage`). 그래서 수정 실패는 중복 답글 없이 재시도하고, 답글 전송 결과를 알 수 없으면 manual_review로 남깁니다. 새 카드를 올린 뒤 답글만 실패해도 카드 ID는 저장하므로 재시도는 그 카드에 답글을 답니다. `not_in_channel`·`channel_not_found`·`invalid_auth` 같은 설정 오류는 `slack_<오류명>` 코드의 영구 오류로 기록합니다. Slack이 일시 오류로 안내하는 `internal_error`·`fatal_error`·`request_timeout`은 카드 수정이면 재시도하고, 새 메시지 전송이면 이미 올라갔을 수 있어 manual_review로 남깁니다. `service_unavailable`은 처리되지 않은 요청이라 둘 다 재시도합니다. 원본 카드가 삭제되어 수정할 수 없으면 새 카드를 올립니다. 수정과 답글은 한 번의 약 10초 HTTP 예산을 나눠 쓰므로, 수정이 느리면 답글 결과가 불확실해져 manual_review로 남을 수 있습니다(중복 전송은 없음). Webhook 방식은 복구만 별도 메시지로 알립니다.
- Notion에는 같은 사건 ID로 상태·종료 시각·요약을 갱신하고, 끝난 이벤트에는 블랙박스 증거 요약 표를 붙입니다. 상세 원본 로그는 PC SQLite에 유지하고 외부에는 선택된 사건 필드와 위 요약만 전송합니다. 요약에는 장치 MAC 기반으로 고른 기록과 AP BSSID가 들어갈 수 있습니다. Notion은 원본 로그의 영구 백업이 아닙니다.
- HTTP는 허용된 HTTPS 호스트에만 연결하고 리디렉션을 따르지 않습니다. 한 전달 작업은 DNS·응답 읽기를 포함해 최대 약 10초의 HTTP 예산을 사용하며, 응답은 64KiB로 제한합니다.
- 429/529는 `Retry-After`를 적용합니다(최대 24시간). 대부분의 4xx는 설정 오류로 분류하고 무한 재시도하지 않습니다. 외부 오류 본문·URL·토큰은 오류 기록에 넣지 않습니다.
- Slack POST 또는 Notion 페이지 생성 직후 응답이 유실되면 실제 저장 여부를 알 수 없습니다. 이 경우 **unknown/manual_review** 상태로 남겨 자동 재전송하지 않습니다. 운영자가 실제 채널/페이지와 사건 ID를 확인해야 합니다. Notion 스키마 읽기·사건 조회와 기존 페이지의 동일 속성 갱신은 안전한 재시도 대상으로 구분합니다. 일시적인 스키마 응답 오류는 쓰기 없이 재시도하며, 스키마 유형·옵션 불일치는 영구 설정 오류로 남깁니다. 설정을 수정한 뒤에는 수집기 DB의 실패한 대기열도 운영 절차에 따라 확인해야 하며, 설정 수정만으로 이전 실패 사건이 자동 재전송되지는 않습니다.
- SQLite 대기열과 사건 ID를 사용해도 외부 API에서 **정확히 한 번 전달**이 보장되는 것은 아닙니다. Slack Incoming Webhook에는 조회·수정용 메시지 ID가 응답으로 반환되지 않습니다. Bot 토큰 방식도 메시지 조회 권한은 쓰지 않으므로 전송 결과가 불확실한 메시지를 자동으로 찾아 정리하지는 않습니다.
- 알림을 중지하려면 `telemetry.incidents.notifications.enabled`를 `false`로 바꾸고 서비스를 재시작합니다. 사건·원본 로그 수집은 별도로 유지됩니다.

## 공식 근거

- [Slack Incoming Webhooks](https://docs.slack.dev/messaging/sending-messages-using-incoming-webhooks/): 비밀 URL, JSON POST, 응답 및 메시지 관리 제한.
- [Slack chat.postMessage](https://docs.slack.dev/reference/methods/chat.postMessage) · [chat.update](https://docs.slack.dev/reference/methods/chat.update): `chat:write` 범위, `ts`·`thread_ts`, 오류 응답.
- [Notion Retrieve a data source](https://developers.notion.com/reference/retrieve-a-data-source): 읽기 전용 속성·상태 옵션 검증.
- [Notion Page property values](https://developers.notion.com/reference/page-property-values): 기존 상태 옵션 이름으로 상태 속성 갱신.
- [Notion Query a data source](https://developers.notion.com/reference/query-a-data-source): 데이터 소스별 필터 조회.
- [Notion 2025-09-03 업그레이드](https://developers.notion.com/guides/get-started/upgrade-guide-2025-09-03): database/data source 분리.
- [Notion 요청 제한](https://developers.notion.com/reference/request-limits): Retry-After, 재시도 제한, 불확실한 쓰기 결과 처리.
- [Notion Append block children](https://developers.notion.com/reference/patch-block-children) · [Retrieve block children](https://developers.notion.com/reference/get-block-children): 페이지 본문에 표 추가, 기존 블록 확인.

단위 검증은 HTTP 대역과 합성 자격 증명만 사용합니다. 일회용 Windows 서비스 CI는 서비스가 중지된 동안 실제 설정 스크립트의 숨김 입력을 합성 값으로 대체하여 DPAPI 왕복·제한된 ACL·기존 설정 보존을 검증합니다. 이후 알림 비활성 설정을 복원한 다음 서비스를 시작하므로 이 시험에서 외부 전송은 발생하지 않습니다. 실제 Slack 메시지 발송이나 Notion 페이지 작성은 수행하지 않습니다.
