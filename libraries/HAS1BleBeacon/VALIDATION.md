# BLE 광고 적용 검증

검증일: 2026-09-19 (KST)

## 적용 범위

- 덕트, 발전기, 탈출 메인, 태그머신 메인에 공통 `HAS1BleBeacon` 라이브러리를 연결했다.
- 아이템박스, 서브 장치, IoT 글러브, 기존 제단/부활기 광고 코드는 이번 변경 대상이 아니다.
- 기존 Wi-Fi와 장치 루프를 처리한 뒤 BLE 설정을 한 단계씩 진행한다. 덕트 개방 중과 태그머신 로그인 중에는 새 BLE 명령을 미룬다.
- 광고는 `HAS3:<device_name>` 형식, 설정 간격 250 ms이다. 이름은 영문/숫자/`_`/`-` 1–18자이다.
- 부팅 시 컨트롤러 초기화는 동기 작업이다. 덕트에서는 초기 서버 명령으로 문 닫기 타이머를 시작하기 전에 초기화를 마친다.

`poll(false)`는 새 설정 명령만 미룬다. 이미 시작한 무선 광고는 계속된다.
이 구조가 Wi-Fi에 무선 자원을 독점시켜 주거나 반응속도 영향을 없애 주는 것은 아니다.

## 자동 검증

| 검증 | 결과 |
| --- | --- |
| BLE 상태 머신 | 15개 시나리오 그룹 통과 |
| 실제 BLE 어댑터 + ESP32 API 대체 구현 | 7개 시나리오 그룹 통과; BLE 합계 22개 그룹 |
| 덕트 쿨타임/오디오 회귀 | 23개 + 9개 시나리오 통과 |
| 탈출 상태 모델 회귀 | 59개 테스트 통과 |
| Telnet 진단 함수 로컬 검사 | 경계값, 잘못된 fd, EAGAIN/부분/0바이트 전송 처리 통과 |
| 독립 코드 검토 | 초기화 순서, 응답 소유권, 실패 복구, 호출 순서와 진단 전송 경로 검토 |

저장소 루트에서 실행:

```sh
python3 libraries/HAS1BleBeacon/tests/run_tests.py
python3 devices/HAS1_duct/tests/run_cooldown_tests.py
python3 -m pytest -q devices/HAS1_escape_main/tests
```

BLE 테스트는 실제 상태 머신과 하드웨어 어댑터 소스를 컴파일해 실행한다.
어댑터의 ESP32 API는 테스트용 대체 구현을 사용한다. AddressSanitizer와
UndefinedBehaviorSanitizer, 엄격한 컴파일 경고 검사를 적용한다.
덕트 테스트는 실제 펌웨어의 관련 로직을 추출해 실행하며, 탈출 테스트는 Python 상태 모델 검증이다.
PC 테스트 결과는 실제 무선 성능이나 ESP32 런타임 힙 측정을 대신하지 않는다.
BLE 테스트에는 이름 변경/비우기, 잘못된 입력, 전송 불가, 응답 거절/누락/지연,
시간값 rollover, 초기화 실패, 즉시·중복 콜백, 바쁜 루프 뒤 응답 소비가 포함된다.
어댑터 검사는 임계 구역 안에서 시간/컨트롤러 API를 호출하지 않는지도 확인한다.

Telnet 진단 검사는 네 장치에 추가한 실제 함수를 추출해 C++11 엄격 경고 검사와
AddressSanitizer/UndefinedBehaviorSanitizer를 적용한 **로컬 임시 검사**이다.
저장소의 테스트 스위트나 CI에 포함된 검사는 아니다. 네 함수의 동일성과 접속 후
1회 호출, 모든 숫자 필드 최댓값에서 315바이트 출력, 18자 이름 제한과 null 이름을
확인했다. 잘못된 fd에서는 전송하지 않고, EAGAIN/부분/0바이트 전송 결과는 각각
`MSG_DONTWAIT` 전송 1회 후 재시도 없이 종료하는 것도 확인했다.

## Telnet 접속 시 진단

네 장치 모두 새 Telnet 클라이언트가 접속하면 `[diagnostics]` 한 줄을 시도한다.
펌웨어 버전, 장치명, Wi-Fi MAC/로컬 IP, free/minimum/largest heap과 BLE
step/radio/error/HCI 상태, 대기 명령, 응답 대기/시간 초과 여부, 명령 수/실패 수를
포함한다. 384바이트 스택 버퍼와 제한된 이름 길이를 사용하며 동적 `String`을
생성하거나 정상 루프에 주기 로그를 추가하지 않는다.

진단 전송은 fd 검사 뒤 `send(..., MSG_DONTWAIT)` 한 번만 수행한다.
버퍼가 막히거나 일부만 전송되면 남은 내용을 버린다. 완전한 진단 줄이 없으면
다시 접속해 새 스냅샷을 받는다. 기존 콘솔 미러링 경로는 변경하지 않았다.
정상 설정 완료 후 `ble_step=7`은 Running, `ble_radio=2`는 컨트롤러가 확인한 On,
`ble_pending=0`은 대기 명령 없음, `ble_error=0`은 None이다.
이 내부 상태와 힙 값은 OTA 적용 확인에 도움이 되지만 **실제 광고 수신 증거를 대신하지 않는다**.

## ESP32 빌드와 용량

Arduino CLI 1.2.2, Arduino ESP32 3.3.11 및 `scripts/firmware_targets.py`의
TTGO-T1 보드/파티션 설정으로 빌드한다. 공통 라이브러리는 `--library`로 명시한다.
빌드 명령 예시는 [README](README.md)에 있다.

비차단 Telnet 진단을 포함한 최종 소스로 네 장치 컴파일·링크를 통과했다.
모든 빌드 입력의 SHA256과 빌드 중 소스 변경 없음도 확인했다. 아래 결과는
배포 워크플로의 버전 증가 전(덕트 50/발전기 16/탈출 35/태그머신 10) 로컬 빌드이다.
탈출 메인은 부팅 버전 보고 추가 후 다시 빌드한 값이다.
실제 릴리즈의 버전·바이너리·의존성은 GitHub Actions 완료 후 별도로 확인한다.

| 장치 | 앱 바이너리 | OTA 앱 슬롯 여유 | IRAM 여유 |
| --- | ---: | ---: | ---: |
| 덕트 | 1,284,240 B | 681,840 B | 2,168 B |
| 발전기 | 1,306,416 B | 659,664 B | 316 B |
| 탈출 메인 | 1,255,440 B | 55,280 B | 3,144 B |
| 태그머신 메인 | 1,257,376 B | 53,344 B | 3,144 B |

앱 바이너리는 `.ino.bin` 파일 크기, IRAM은 링크 맵의 `iram0_0_seg` 시작부터
`_iram_end`까지의 점유량을 기준으로 계산했다. IRAM 용량은 131,072 B이다.
이 빌드에서 발전기는 링크에 성공했지만 IRAM 여유가 매우 적었다. 인터럽트 루틴이나
라이브러리를 바꿀 때 다시 링크 용량을 확인해야 한다. 탈출/태그머신은 기본
OTA 슬롯 1,310,720 B 중 약 95%를 사용하므로 향후 앱 크기 증가에도 주의해야 한다.

라이브러리 버전은 배포 워크플로에 맞춘 레지스트리 패키지를 사용했다.
커스텀 HAS2_Wifi/SecureOTA/SimpleTimer는 로컬 준비본으로 빌드했으며,
HAS2_Wifi와 SecureOTA 준비본은 배포 직전 원격 소스와 바이트 단위 일치를 확인했다
(HAS2_Wifi `fe06380fa376b6438b9c22de2486678cc6ac6907`, SecureOTA
`162db758e6806895ef10ca39b101f9f8753bdc20`). 이 표는 GitHub Actions 실행 결과는 아니다.
정적 메모리/링크 성공만으로 Wi-Fi·BLE 초기화 후의 실제 남은 힙을 판단할 수는 없다.

## 릴리즈 및 병렬 배포 검증

덕트 v51 [CI 배포](https://github.com/Fuzzyline-HAS2/New_HAS1/actions/runs/35424553134)가
성공했다. 배포 바이너리는 1,282,736 B로 OTA 슬롯에 들어가며, version.txt=51,
서명 파일 32 B와 다운로드 전후 자산 메타데이터 일치를 확인했다. 빌드 시작은
`7da757c`, 배포 커밋은 `759d8c8`이며 사이 변경은 덕트 버전 증가뿐이다.

다른 장치의 빌드는 병렬 실행하며 같은 장치의 고정 릴리즈는 concurrency group으로
직렬화한다. 실제 SecureOTA `_push_with_retry`를 임시 bare Git과 3개 clone에서
동시에 실행해 세 장치 버전 커밋 보존, non-fast-forward 후 fetch/rebase,
로컬 바이너리/서명 보존 및 남은 stash 0을 확인했다. 배포 중에는 빌드 입력을
바꾸지 않으며, 이 검증은 서로 다른 장치의 버전 커밋만 겹치는 경우를 대상으로 한다.

## 실기 테스트: 진행 중

TD에 v51 OTA 요청을 전달했으나 이 문서 작성 시점에 새 버전 보고는 확인 전이다.
**BLE 무선 수신, 장치 동작 및 Wi-Fi 지연 비교는 아직 검증하지 않았다.**
현재 Mac이 대상 장치의 로컬 네트워크와 달라 Telnet 직접 진단이 제한되며,
호스트 테스트와 로컬 빌드 통과를 실물 검증 완료로 해석해서는 안 된다.

macOS CoreBluetooth 수신 도구는 준비했지만, 샌드박스 밖에서 읽은 기존 Bluetooth
권한은 `notDetermined`였다. 권한 조회만 수행했고 manager 생성이나 스캔은 하지 않았다.
수신 테스트에는 Bluetooth 접근이 허용된 호스트 또는 외부 BLE 스캐너가 필요하다.
macOS 수신 도구는 Wi-Fi MAC 대신 peripheral UUID를 반환하므로 광고명과
Telnet의 장치명/MAC/IP를 함께 비교해야 한다.

같은 장치에서 기존 펌웨어와 변경 펌웨어를 비교한다. AP, 전원, 설치 위치,
서버 명령 간격을 같게 유지하고 다음 결과를 기록한다.

| 항목 | 확인 내용 |
| --- | --- |
| 광고 | BLE 스캐너에서 `HAS3:<실제 이름>`과 scan response 확인, 이름 변경/빈 이름에 따른 변경·중지 |
| Wi-Fi | 주기 보고와 서버 명령 응답의 지연 분포·최대 지연, 재접속 및 누락 비교 |
| 덕트 | 버튼·비상 입력, 문 닫기 시각, 개방 중 이름 변경, 서버 초기 상태가 open/mo인 부팅 |
| 발전기 | 엔코더·배선 감지, RFID, MP3 재생 중 명령 누락·오동작 비교 |
| 탈출 메인 | 모터 이동·끝단 감지·서브 통신 중 오동작, 이동 전후 서버 응답 비교 |
| 태그머신 메인 | 태그 인식·로그인·게이지와 서브 통신, 로그인 중 이름 변경 후 유휴 시 반영 |
| 안정성 | 부팅 전후 free/minimum heap·largest free block, 반복 동작과 Wi-Fi 재연결 중 재부팅/워치독 여부 |

IoT 글러브의 방 판정은 별도 확인 항목이다. 광고가 스캔되더라도 실제 장치 이름이
`devices/iotglove/iotglove_beetle/beacon_map.h`에 방과 연결되어 있지 않으면 위치 판정에 사용되지 않는다.
이번 변경은 해당 매핑을 추가하지 않았다.
